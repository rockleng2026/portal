## 2. 必修的缺陷（已修复）

### P0-01 · 自然人闸门看的是"有没有 employee_id"，不是"是不是人"

`AuthenticatedClient.isHuman()` 原本是 `employeeId != null`。任何带 `employee_id` 的机器账号
都能通过 10 个人工专属端点（授权、审批、Kill-Switch、Agent 生命周期、终端绑定）。
测试夹具自己就建了 `principal_type='service'` + `employee_id` 的"人"账号，于是这条路径从未被真正测到。

**修复**：`isHuman()` 改为 `principal_type == "human" && employeeId != null`；DDL 词表同步修正
（V6）；测试夹具改成 `human`；并新增 `role` / `dept_id` 两列，用来表达"这个自然人能审批到什么层级"。

### P0-02 · 不可逆动作一个人就能批（双重审批形同虚设）

`PolicyEngine` 会把 `cap:db.ddl` 判成 `DUAL_CISO`，`ApprovalStateMachine` 里有
`assertDualApprovalComplete()`，但平台流程**从不调用它**——一次点击就 `APPROVED`。
02 §结论 2 把"AI 不能给自己授权"列为不可妥协的底线，这条是它的一半。

**修复**：新增 `harness_approval_signoff` 表记录每一次签字；`DUAL_CISO` 的审批在只有 1 个签名时
**保持 pending**，第 2 个**不同的**自然人签字才转 `approved`。同一个人的两次签名不算两个人
（有测试）。

### P0-03 · 审批层级被算出来然后扔掉

`requiredApproverScope()` 的结果只被当作审计字符串存起来，谁审批都不校验：任意一个控制台账号
都能批跨部门甚至 R4 的提权。

**修复**：`ApprovalService` 按层级校验审批人——跨部门要 `system_admin`，本部门要该部门的
`dept_director`；**驳回不受此限制**（拒绝永远比批准更容易，否则会逼人批准）。

### P0-04 · 全局 Kill-Switch 会被更窄的开关盖掉

`KillSwitchState.activeFor()` 原先"最具体的赢"。于是 `global:halt` + `agent:to_l0` 时，
L0 只读能力（`min_level=0`）**照常放行**——"一键停机"在最需要的时候不生效。

**修复**：改为"**限制性最强**者胜"（TO_L0 < STOP < HALT），同级时更具体者胜。
另修了一个解析缺陷：`cap:xxx` 里的冒号让 `scope:scopeId:effect` 的切分错位，
**能力维度的 Kill-Switch 根本无法被解析出来**。

### P0-05 · 吊销只断了心跳，没断凭据

`TerminalService.revoke()` 改了 `harness_terminal.status`，但设备对应的 `harness_principal`
仍然是 `active`——被吊销的设备照样能 `POST /api/harness/event`、`POST /api/harness/policy/check`。
A0-5 写的是"失去**全部**能力"。

**修复**：吊销同时把该终端的 principal 置为 `disabled`；认证层再加一道（终端被吊销 → 403）。

### P0-06 · 授权范围可以被请求方放宽

`Scope.intersect()` 把**请求方**的 `rowFilter` / `resourcePerm` 覆盖到授权方之上。
一个持有 `owner=me` 的授权，可以被一个 `owner=everyone` 的请求放大成全组织。
"能力 ∩ 作用域 ∩ TTL"里的 ∩ 变成了 ∪。

**修复**：同名键取值冲突即交集为空；`resourcePerm` 冲突同样返回空。请求方永远不能放宽授权方。

### P0-07 · UUIDv7 的 48 位时间戳装反了

`Ids.uuid7()` 把时间戳的**低 32 位**放在了 UUID 字符串的前 8 个十六进制位，
高 16 位放在后面。后果：字符串序只在 2^32 毫秒（约 49.7 天）内单调，
且任何按 RFC 9562 读的实现（Postgres `uuidv7()`、Python/Go 的 uuid 库）读出的时间戳是错的。

**修复**：按 RFC 9562 §5.7 逐字节重排（时间戳占最高 6 字节）。
新增测试：跨毫秒排序、48 位时间戳往返。

### P1-08 · `api_scope` 的通配符比较是失效的

`AuthFilter` 里的判断是 `!scope.endsWith("*") && !scope.equals(uri)`：
带 `*` 的 scope 直接短路，**前缀根本没比**；不带 `*` 的又要求完全相等。
一旦签发一个窄 scope 的账号，它就拿到了全部端点。

**修复**：按"路径前缀"实现（`/api/harness/terminal/*` 只覆盖 terminal 下的端点）。
另外删掉了 `/api/harness/internal/**` 的免鉴权豁免——一个没人用的口子。

### P1-09 · 机器账号可以冒充自然人出现在审计里

`actorId()` 只在 `principal_type == "human"` 时才写 `human:`，控制台账号落到了
`system:<clientId>`。于是"谁批的这条提权"在审计里是 `system:...`。
P0-01 修好之后这一条自动成立（`decided_by` 现在写 `human:<employeeId>`）。

### P1-10 · 授权可以借用别人的 grant

策略引擎只按 `cap_id` 匹配授权，不校验 `agent_id`。属于 A 的授权能授权 B。
平台层碰巧只查了 A 的授权，所以当前不可利用，但这是纵深防御的缺口。

### P1-11 · 空白 `source_ref` 冒充引用

不可信内容的校验只判断"集合非空"，`Set.of("   ")` 就能过。
R-05 要求的是"引用得上"，不是"有个字符串"。

### P1-12 · 能力令牌没有 TTL 上限

`CapabilityToken.mint()` 把 TTL 策略"交给调用方"，30 天的令牌照样签发、照样通过校验。
03 §5 写的是 TTL ≤ 24h，联邦 ≤ 1h。

### P1-13 · 终端的本地策略构造即崩溃

`LocalPolicy` 构造函数在遍历 `allowedRoots` 的同时往里 `add` —— 第一次使用必然
`ConcurrentModificationException`。而且它**不在 Maven reactor 里**，所以从来没被编译过。

### P1-14 · 审批令牌与命令不绑定

`LocalPolicy.check()` 只看令牌的 `approvalId` / 过期时间 / 是否用过，
**从不比较**令牌的 `command` / `capKey` / `targetPath`。
一份"删 `/srv/data/a.txt`"的签字可以用到"删 `/srv/data/b.txt`"上。

### P1-15 · 设备私钥明文落盘、目录权限过宽

`DeviceIdentity` 把设备密钥以明文 base64 写在 `device.key` 里，且不设权限。
R-01 明确要求"禁止落盘明文"。

## 3. 平台与 portal 侧的系统性缺口（已修复）

| 缺口 | 后果 | 修复 |
|---|---|---|
| 没有任何"自然人"账号的创建途径 | 所有人工事务端点在真实部署里**不可达** | 启动时用 `HARNESS_HUMAN_*` 引导第一个控制台账号 |
| `/policy/check` 的 `contentTrust` 缺省为 trusted | 省略字段即拿到可信通道 | 改为**必须显式声明**，否则 400 |
| 终端静默 15 分钟不会自动降权 | R-01 / A0-6 只在文档里 | 定时作业把静默终端置 `offline`，策略层对离线终端拒绝写操作 |
| 超时审批不会自动过期 | 待办里堆着一排永远 pending | 定时作业自动过期 |
| Kill-Switch 的"终端"粒度匹配不上 | 第 5 个粒度是摆设 | 策略请求现在带 `terminalId` |
| 拒绝的治理动作不留审计 | "谁尝试过越权"查不到 | 生命周期非法迁移、TTL 超限等拒绝路径全部补审计 |
| portal 的 `/api/harness/**` 整个命名空间 404 | 平台侧接口全不可用 | `web.xml` 增加 filter 映射；按 `alwaysSelectFullNamespace=true` 拆成三个 package |
| portal 的配置文件路径错 + 初始化时机错 | 命名空间永远是 503 | 路径改 `/WEB-INF/props/...`；改为首次请求时惰性加载 |
| portal 验签后没有把请求体回填 | 所有 POST 收到空参数 | 安装缓存请求并解析 JSON 到 `harness.parameters` |
| portal 先占用 nonce 再验签 | 攻击者可以烧掉合法客户端的 nonce | 改成**验签通过后**才占用 |
| portal 只有 2/6 条登录路径拒绝数字员工 | A0-2 的"全部失败"不成立 | 6 条凭据查询全部加 `isAI=0`；`isAI` 查询失败改为**失败关闭** |
| `blast_radius` 是 TINYINT，种子值 1000 被截断成 127 | 最高风险能力的"影响半径"是错的 | V6 改成 `INT` 并恢复种子值（真实 MySQL 8 已验证） |
| 跨系统 HMAC 靠人工脚本比对 | 已经漂移过一次 | `verify-portal-interop.sh` 现在自动编译并比对**三方**（portal / platform / terminal）签名 |

## 4. 终端：两个东西，两套实现

评审时仓库里有**两个**终端，都不成立：

* `harness-terminal/`（Rust，根目录）：不在任何构建里、无任何引用、**编译不过**
  （`Cargo.toml` 缺 `pymysql`/`rand`/`hmac`/`sha2`；代码用 clap 3 的 `App`，依赖声明的是 clap 4；
  `matches.is_present("install")` 引用了未定义的参数会 panic）。
  它直连 MySQL、用 root 账号、口令硬编码在源码里，自己往库里写绑定码——这与
  "终端不碰业务库、绑定码由平台签发、终端只走 HMAC 服务账号"整套设计相反，
  而且绕开了吊销与审计。它查的 `harness_terminal` 表还有两列在 03 §2.1 的 DDL 里并不存在，
  连库名（`harness_terminal` vs `harness`）都不一样。

* `harness/harness-terminal`（Java，harness 工程内）：设计上是终端设备外壳的正确位置
  （README 明确"protocol 会被原样嵌进终端运行时，一份代码三平台分发"），
  但只有 3 个类、**不在 reactor 里**、没有 `TerminalMain`（shade 插件指向的主类不存在），
  `LocalPolicy` 构造即崩。

现在这两个位置各归其位：

### 4.1 `harness/harness-terminal`（Java）= 设备外壳

* 设备身份（重启不变、密钥 0600、不写明文口令）
* 平台客户端（HMAC 签名与平台逐字节一致，有跨模块互认测试）
* 绑定码流程（`hello` → 平台发码 → 自然人在控制台输入 → `bind`）
* 心跳循环 + 被吊销时立即放弃能力
* 本地拒绝策略（能力 / 等级 / 路径白名单 / 审批令牌 / 审批范围绑定）
* CLI：`install / status / hello / bind / heartbeat / run / revoke`
* 可执行产物：`harness-terminal-0.1.0-SNAPSHOT.jar`（自包含，80 KB）

### 4.2 `harness-terminal/`（Rust）= 终端智能体运行时

这一版是**重写**的，不是修补——原来的代码没有一行能复用。它现在是一个完整的 coding agent：

| 要求 | 实现 |
|---|---|
| 收集上下文 | `workspace.rs`：遍历工作区、识别 40+ 种语言、按语言与体积统计、忽略噪声目录；`agent::build_context_packs` 按任务关键词把相关文件打进预算内的上下文包 |
| 采取行动 | `tools/`：`read_file` / `write_file` / `edit_file`（精确替换，**不唯一就拒绝改**）/ `delete_file` / `list_files` / `search_code` / `shell_exec` / `run_tests` / `git_status` / `git_commit` |
| 验证结果 | 工具返回**原样**输出（编译错误、测试输出、diff），`run_tests` 额外抽出失败用例摘要 |
| 自主循环 | `agent/mod.rs`：`模型 → 工具调用 → 策略检查 → 执行 → 结果回灌 → …`，带步骤预算与上下文预算，产出 `TaskOutcome` 与可回放的 transcript |
| 扩展（skill/MCP） | `skills/mod.rs`：SKILL.md + frontmatter + scripts/，**坏 frontmatter 报错不忽略**；`mcp/mod.rs`：stdio JSON-RPC 客户端（`initialize` → `tools/list` → `tools/call`） |
| 多模型 | Anthropic Messages API / OpenAI chat-completions / `ScriptedModel`（离线回放，测循环用） |
| 直接操作与执行 | 编辑文件、创建 git 提交、运行测试与 shell 命令 |

**和普通 coding agent 的区别是它受治理约束**：每次工具调用先过 `policy::LocalPolicy`
（能力 / 自治等级 / 路径白名单 / 绑定到命令与路径的人工审批令牌）。平台被攻破、边缘层撒谎、
工具参数被投毒，都绕不过本地的拒绝规则。技能与 MCP 是**内容**不是授权：MCP server 不能自授能力。

构建：`cargo build --release`（7.2 MB 单二进制），`cargo test` → **38 tests 全绿**。
命令行：`run` / `inspect` / `tools` / `replay`。

**仍然缺**：03 §3 的 TCP 帧通道与边缘层（平台目前只有 HTTP）；MCP 工具目前只注册进目录、
实际调用要由会话发起；本地模型（Qwen3.8B）尚未接入。

规格文档 `03-协议与数据模型.md` 之前描述的是一个**装不出来的 schema**和一条**防不住改写的签名**。
两条都已回写，errata 文件标记 CLOSED。

**E-01（`harness_event` 引用了不存在的列）**

* §2.2 的列清单补上 `event_window VARCHAR(64) NOT NULL DEFAULT 'none'`；
* 新增一张表写死**去重窗口粒度**：`realtime` → 1 分钟、`nearline` → 1 小时、`batch` → 1 天，
  取值形如 `r3421` / `n289744` / `b20537`；并写明"运维要更粗的窗口就改桶大小，不要改去重语义"；
* 顺带改正了 `fingerprint` 的注释：原文写 `source+key+hash(window)`，实现算的是
  `source + businessKey + sha256(canonical(payload))`——payload 的哈希，不是窗口的哈希。
  两处各说各话会让下一个人照着错的写。

**E-05（帧 MAC 未覆盖 type/flags/length）**

* §3.1 写死 MAC 覆盖范围：`MAGIC ‖ VERSION ‖ TYPE ‖ FLAGS ‖ LENGTH ‖ SEQ ‖ NONCE ‖ PAYLOAD`
  （尾部 32 字节 MAC 除外），并说明早先写法为什么挡不住"把 `CMD` 改写成 `EVENT`"；
* 补两条**实现要求**：签名字节必须由**收发两侧共用**的方法产出（`Frame.signedBytes()`），
  不得各写一遍；**`VERSION` 不被容忍**——版本号不认识的帧整帧拒绝并断开连接，不做"尽力解析"；
* §10 补上"帧格式或 MAC 覆盖范围一改，`VERSION` 必须 +1，边缘与终端同时升级"，
  并说明 `N-1` 窗口从第二个版本开始才有意义（当前 `VERSION=1` 是首个发布版本）；
* 代码侧补了 `FrameCodec.readAndVerify()`——原来的 `read()` 只检查结构、不验 MAC，
  返回的帧"看起来能用"，是个陷阱；现在有测试钉住"未知版本被拒""LENGTH 被改则 MAC 失效"
  "MAC 不对则拒收"。

**顺带回写 §4 事件规范**：规则 1（引用才可执行）与规则 2（注入降级为 L0 报告）的落法写清楚了，
包括"检测器不是安全边界"和"指纹不参与检测结论"。

### 每台设备一个机器账号（本轮补上）

之前所有终端共用 `harness-bootstrap` + 同一个密钥——**一台机器泄露就能冒充所有机器**，
吊销一台设备会连坐所有设备，审计里也分不清是谁在说话（red-team R-01）。

现在：

* 控制台「终端」页签 → **「新建设备账号」**（自然人）→ 得到 `dev-<随机>` 的 client id、
  **只显示一次**的密钥，和填好的安装命令；
* 平台存的是 `sha256(secret)`，所以**密钥平台自己给不出来**——这一点没有变，也不该变；
* 设备账号的作用域只有 `/api/harness/terminal/*,/api/harness/tasks/*`，
  设备第一次 `hello` 时**绑定到自己那台终端**，之后只能替自己说话
  （读别人的授权 → `403 NOT_YOUR_TERMINAL`）；
* 吊销一台设备 → 只失效它自己的账号。

实测（本机）：

| 动作 | 结果 |
|---|---|
| 自然人建设备账号 | `clientId=dev-cf9190dafe99`，密钥只返回一次，库里存的是哈希 |
| 机器账号想建账号 | 403 `HUMAN_REQUIRED` |
| 设备账号读**自己的**授权 | 200 |
| 设备账号读**别人的**授权 | 403 `NOT_YOUR_TERMINAL` |
| 设备账号想读审计 | 403 `SCOPE_NOT_ALLOWED` |

### 常驻智能体实时感知授权变化（本轮补上，2026-10-29）

之前那条链是「外壳取回授权 → 写 `grant.json` → 智能体读文件」，而**智能体只在启动时读一次**。
后果：平台收权之后，那台机器上的常驻智能体**仍然按旧授权继续干活**，直到有人去那台机器上
重启它。这不是「权限收敛」没做，是**收敛的对象没随时间更新**——红队 R-01 的后半段。

两个洞，都补了：

1. **智能体只读本地文件，不问平台**。改成：常驻循环每 10 秒向平台问一次
   `GET /api/harness/terminal/{id}/grant`，把答案重写进本地 `grant.json`
   （先写临时文件再改名，不会读到半截），并换掉自己手里的权限。
   本地文件仍然只是**副本**，权威始终在平台。
2. **授权文件读不出来，等于没有授权**。平台的 `autonomyLevel` 之前发的是**字符串** `"3"`，
   Rust 端按数字解析 → 整个 JSON 解析失败 → 智能体一直是「no grant」。
   平台改成发**数字**；Rust 端也**兼容带引号的数字**（老部署可能还在发字符串）。
   测试里补了一条：`a_quoted_autonomy_level_is_still_read`。

实测（目标机 `192.168.0.65`，智能体进程**全程没有重启**）：

| 动作 | 智能体的反应 |
|---|---|
| 平台吊销 `cap:ssh.exec` | 约 10 秒后日志出现 `grant changed: ... [cap:file.read, cap:file.write]` |
| 之后下发 `whoami` | **拒绝执行**：「这个能力没给过我」（`cap:ssh.exec was never granted`） |
| 平台重新授权 `cap:ssh.exec` | 约 15 秒后日志出现 `grant changed: ... [cap:file.read, cap:file.write, cap:ssh.exec]` |
| 再下发 `whoami` | **真的执行了**，回答「当前用户是 aios」 |
| 改授权层级 / 换能力集 | 同上，走同一条路径 |

顺带修掉的：平台发 `autonomyLevel` 的地方改成数字后，Java 终端外壳（`int autonomyLevel`）
与 Rust 端（`u8`）的读法就对齐了；Java 侧那条断言原来写成 `value("2")`，Spring 会把数字
转成字符串再比，所以**类型错了也测不出来**——已收紧成 `value(2)`。

### 平台用 fat jar 跑 → 所有签名请求挂死（2026-10-29）

用户报「发送失败：NetworkError when attempting to fetch resource」，点开数字员工的对话
也报错。抓下来看：`GET /api/harness/tasks` **挂着不返回**（5 分钟无响应），而 MySQL
里**一条查询都没有**——说明请求卡在数据库之前。

根因在日志里：平台是以 Spring Boot **fat jar** 跑的（`java -jar`）。fat jar 把依赖放在
`BOOT-INF/lib`，用**自己的类加载器**加载；而 Tomcat、Netty、连接池**自己创建**的线程
不用这个加载器：

```
Exception in thread "http-nio-18080-exec-2" java.lang.NoClassDefFoundError: ch/qos/logback/classic/spi/ThrowableProxy
Exception in thread "lettuce-nioEventLoop-4-1" java.lang.NoClassDefFoundError: io/netty/buffer/PoolArena$1
```

* **Lettuce 的事件循环线程死了** → Redis 不再应答 → 每个签名请求都要写的 **nonce**
  永远等不到 → 请求挂死 → 浏览器只看到 NetworkError；
* Tomcat 的 JUL→logback 桥同样炸 → **连错误日志都打不出来**（所以日志里只剩
  `NoClassDefFoundError` 本身，看不到原来那个错）；
* 同一根因还顺手弄坏了优雅停机（`GracefulShutdownCallback`）、连接池清理
  （`LinkedBlockingDeque$Node`）。

修法：**不用 fat jar**。`harness/tools/harness-platform.sh` 先把 jar 解开
（`java -Djarmode=layertools -jar … extract`），再用**普通 classpath** 启动：

```bash
java -cp "exploded/application/BOOT-INF/classes:exploded/application/BOOT-INF/lib/*:exploded/dependencies/BOOT-INF/lib/*" \
     com.fuao.harness.platform.PlatformApplication
```

每个类对每个线程都可见 ✓。实测：修之前 `GET /api/harness/tasks` 挂 5 分钟无响应；
修之后同样的请求 **30 毫秒**返回，连续 60 次签名请求 2.2 秒跑完，日志里
**一条异常都没有**，Lettuce 线程也活着（`jcmd Thread.print` 里 runnable ✓）。

顺带修的两处：

* systemd 单元改用 `ExecStart=/bin/bash …/harness-platform.sh run`——systemd 的
  `PATH` 很短，脚本里的 `dirname`/`mvn` 会找不到（脚本也改成不依赖外部命令）；
* `~/.harness/platform.env` 的 `PATH` 不再引用继承来的 `$PATH`（systemd 给的那份
  只有几个目录）。

### 数字员工入职 portal：部门写成了 1，工号是业务键（2026-10-30）

### 控制台「数字员工 → 对话」显示的是别人的对话（2026-10-29）

用户报的现象：**在每个数字员工后面点「对话」，弹出来的聊天内容都一样。**

复现（jsdom 跑真控制台脚本，对真平台点一遍）：

| 步骤 | 现象 |
|---|---|
| 点 **zhangshan**（有终端） | 面板打开，15 条记录，副标题「zhangshan」 ✅ |
| 再点 **leon3**（没绑终端） | 面板**不关**，还是那 15 条记录、副标题还是「zhangshan** ❌ |

两个洞：

1. `openChat(null)` 只弹了个 toast 就 `return`，**旧面板留在屏幕上**——所以「每个员工
   点出来都一样」（看起来像是同一个员工的对话）；
2. 员工**可能绑着多台终端**（换机器了、旧的还没拆），控制台取的是列表里的**第一台**，
   可能是已经离线的旧机器，于是打开的是它的旧记录。

修法：

* 没有终端就**关掉面板**（连日志一起清），并点名说清是哪个员工没有终端；
* 「跟哪台终端对话」这条规则**收到平台侧**：`/api/harness/agent` 多带一个 `terminalId`
  ——在线的优先，其中心跳最新的优先（`TerminalService.liveTerminalOf`）；
* 面板只显示这台终端自己的任务：切换终端时**先停掉旧轮询**，并且把回来的任务按
  `terminalId` 过滤一遍（在途的旧响应不会倒进新面板）。

回归检查收进仓库：`harness/tools/check-console-chat.js`（jsdom + 真平台），
检查「内容属于它自己 / 没有别的终端的内容 / 没终端的员工不留旧对话」三件事。

### portal 侧在本机跑通了（2026-10-27）

把 portal 真正跑起来，暴露了 6 个**只有真跑才会出现**的问题，都已修：

| 问题 | 现象 | 修法 |
|---|---|---|
| 命名空间没被 Struts 认领 | `/api/harness/**` 全部 404 | `alwaysSelectFullNamespace=true` 下，命名空间取"最后一个斜杠之前" → **每个 URL 段一个 package** |

| 签名路径不一致 | 平台侧签名 `/api/...`，portal 签 `getRequestURI()`（含 context path `/portal`） | 两侧都签 **context 内的路径**（servletPath + pathInfo） |
| `CheckCacheFilter` 把请求送去登录页 | 有 session 才放行 | harness 命名空间用 HMAC 自认证、永远没有 portal session → 显式放行 |
| XML 编码与声明不符 | Struts 解析报 "Invalid byte 1 of 1-byte UTF-8 sequence" | XML 由**声明**决定编码，`.java` 才由 javac 的 `-encoding` 决定；新增的 `struts-harness.xml` 补回 Struts 的 DOCTYPE |

| 签名的 `GET /portal/api/harness/health.do` | `200 {"status":"ok","service":"portal-harness-api"}` |
| 签名的 `POST /portal/api/harness/permission/snapshot.do` | 返回员工的原始权限串与解析结果 |
| 签名的 `POST /portal/api/harness/agent/onboard.do` | **数字员工真的入职了**：`employee` id=326 / uuid=agent:leon:portal:sh001，`users` isAI=1 |

### 智能体与设备外壳的接线（本轮补上）

按建议方案落地：**一个权威、两处执行**。

```
平台 harness_grant ──HMAC──▶ Java 外壳 ──写 grant.json(0600)──▶ Rust 智能体
   （唯一权威）              （取回 + 落地）              （读同一份文件并执行）
```

* 平台新增 `GET /api/harness/terminal/{id}/grant`：返回该终端当前持有的能力集、
  自治等级与所属部门。授权来自 `harness_grant`，**撤销/过期自动从列表里消失**——
  平台是唯一能回答"现在能做什么"的地方。
* Java 外壳新增 `harness-terminal grant`：用 HMAC 取回并写入
  `~/.harness/terminal/grant.json`（0600）。文件里**不含审批令牌**——
  审批是给单条命令签的，跟着命令走，绝不预先分发。
* Rust 智能体新增 `grant` 模块：启动时读同一份文件建策略。给了 `--identity` 就以
  grant 为准（**没有 grant 就什么都不能做**）；不给 `--identity` 就是"有人坐在机器前"的
  独立运行模式，会明说 `standalone: no platform grant`。

端到端已验证：有 grant → `read_file` 成功、文件进 touched；没有 grant →
`CAPABILITY_NOT_GRANTED`，transcript 里留痕。文件格式两侧都有测试钉住（camelCase）。

### 注入检测器（本轮补上）

* `harness-protocol`：`InjectionDetector`——七类信号（改写指令 / 绕过审批 / 外传凭据 /
  敏感路径 / 破坏性命令 / 角色冒充 / 暗中行事），中英双语；只扫不可信内容，指令通道不扫；
  指纹不因检测结果改变（去重不受影响）。
* `EventEnvelope` 携带 `suspectedInjection` 与 `injectionReasons`。
* 平台：命中即 `status='suspected'`（**不作为工作派发，等人看**）+ 写
  `event.injection_detected` 审计告警。
* 语料：38 条注入样本全部命中（设计要求 ≥95%），14 条普通业务文本零误报——
  第一版规则有两条误报（"提到审批"不等于"绕过审批"）和三条漏检，是语料测出来的。
* **它不是安全边界**：边界仍然是策略引擎的"引用才可执行"。检测器只负责**降级 + 告警**。
