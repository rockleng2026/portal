## 2. 必修的缺陷（已修复）

### P0-01 · 自然人闸门看的是"有没有 employee_id"，不是"是不是人"

`AuthenticatedClient.isHuman()` 原本是 `employeeId != null`。任何带 `employee_id` 的机器账号
都能通过 10 个人工专属端点（授权、审批、Kill-Switch、Agent 生命周期、终端绑定）。
测试夹具自己就建了 `principal_type='service'` + `employee_id` 的"人"账号，于是这条路径从未被真正测到。

**修复**：`isHuman()` 改为 `principal_type == "human" && employeeId != null`；DDL 词表同步修正
（V6）；测试夹具改成 `human`；并新增 `role` / `dept_id` 两列，用来表达"这个自然人能审批到什么层级"。

### P0-02 · 不可逆动作一个人就能批（双重审批形同虚设）

`PolicyEngine` 会把 `cap:db.ddl` 判成 `DUAL_CISO`，`ApprovalStateMachine` 里有
`assertDualApprovalComplete()`，但平台流程**从不调用它**——一次点击就 `APPROVED`。
02 §结论 2 把"AI 不能给自己授权"列为不可妥协的底线，这条是它的一半。

**修复**：新增 `harness_approval_signoff` 表记录每一次签字；`DUAL_CISO` 的审批在只有 1 个签名时
**保持 pending**，第 2 个**不同的**自然人签字才转 `approved`。同一个人的两次签名不算两个人
（有测试）。

### P0-03 · 审批层级被算出来然后扔掉

`requiredApproverScope()` 的结果只被当作审计字符串存起来，谁审批都不校验：任意一个控制台账号
都能批跨部门甚至 R4 的提权。

**修复**：`ApprovalService` 按层级校验审批人——跨部门要 `system_admin`，本部门要该部门的
`dept_director`；**驳回不受此限制**（拒绝永远比批准更容易，否则会逼人批准）。

### P0-04 · 全局 Kill-Switch 会被更窄的开关盖掉

`KillSwitchState.activeFor()` 原先"最具体的赢"。于是 `global:halt` + `agent:to_l0` 时，
L0 只读能力（`min_level=0`）**照常放行**——"一键停机"在最需要的时候不生效。

**修复**：改为"**限制性最强**者胜"（TO_L0 < STOP < HALT），同级时更具体者胜。
另修了一个解析缺陷：`cap:xxx` 里的冒号让 `scope:scopeId:effect` 的切分错位，
**能力维度的 Kill-Switch 根本无法被解析出来**。

### P0-05 · 吊销只断了心跳，没断凭据

`TerminalService.revoke()` 改了 `harness_terminal.status`，但设备对应的 `harness_principal`
仍然是 `active`——被吊销的设备照样能 `POST /api/harness/event`、`POST /api/harness/policy/check`。
A0-5 写的是"失去**全部**能力"。

**修复**：吊销同时把该终端的 principal 置为 `disabled`；认证层再加一道（终端被吊销 → 403）。

### P0-06 · 授权范围可以被请求方放宽

`Scope.intersect()` 把**请求方**的 `rowFilter` / `resourcePerm` 覆盖到授权方之上。
一个持有 `owner=me` 的授权，可以被一个 `owner=everyone` 的请求放大成全组织。
"能力 ∩ 作用域 ∩ TTL"里的 ∩ 变成了 ∪。

**修复**：同名键取值冲突即交集为空；`resourcePerm` 冲突同样返回空。请求方永远不能放宽授权方。

### P0-07 · UUIDv7 的 48 位时间戳装反了

`Ids.uuid7()` 把时间戳的**低 32 位**放在了 UUID 字符串的前 8 个十六进制位，
高 16 位放在后面。后果：字符串序只在 2^32 毫秒（约 49.7 天）内单调，
且任何按 RFC 9562 读的实现（Postgres `uuidv7()`、Python/Go 的 uuid 库）读出的时间戳是错的。

**修复**：按 RFC 9562 §5.7 逐字节重排（时间戳占最高 6 字节）。
新增测试：跨毫秒排序、48 位时间戳往返。

### P1-08 · `api_scope` 的通配符比较是失效的

`AuthFilter` 里的判断是 `!scope.endsWith("*") && !scope.equals(uri)`：
带 `*` 的 scope 直接短路，**前缀根本没比**；不带 `*` 的又要求完全相等。
一旦签发一个窄 scope 的账号，它就拿到了全部端点。

**修复**：按"路径前缀"实现（`/api/harness/terminal/*` 只覆盖 terminal 下的端点）。
另外删掉了 `/api/harness/internal/**` 的免鉴权豁免——一个没人用的口子。

### P1-09 · 机器账号可以冒充自然人出现在审计里

`actorId()` 只在 `principal_type == "human"` 时才写 `human:`，控制台账号落到了
`system:<clientId>`。于是"谁批的这条提权"在审计里是 `system:...`。
P0-01 修好之后这一条自动成立（`decided_by` 现在写 `human:<employeeId>`）。

### P1-10 · 授权可以借用别人的 grant

策略引擎只按 `cap_id` 匹配授权，不校验 `agent_id`。属于 A 的授权能授权 B。
平台层碰巧只查了 A 的授权，所以当前不可利用，但这是纵深防御的缺口。

### P1-11 · 空白 `source_ref` 冒充引用

不可信内容的校验只判断"集合非空"，`Set.of("   ")` 就能过。
R-05 要求的是"引用得上"，不是"有个字符串"。

### P1-12 · 能力令牌没有 TTL 上限

`CapabilityToken.mint()` 把 TTL 策略"交给调用方"，30 天的令牌照样签发、照样通过校验。
03 §5 写的是 TTL ≤ 24h，联邦 ≤ 1h。

### P1-13 · 终端的本地策略构造即崩溃

`LocalPolicy` 构造函数在遍历 `allowedRoots` 的同时往里 `add` —— 第一次使用必然
`ConcurrentModificationException`。而且它**不在 Maven reactor 里**，所以从来没被编译过。

### P1-14 · 审批令牌与命令不绑定

`LocalPolicy.check()` 只看令牌的 `approvalId` / 过期时间 / 是否用过，
**从不比较**令牌的 `command` / `capKey` / `targetPath`。
一份"删 `/srv/data/a.txt`"的签字可以用到"删 `/srv/data/b.txt`"上。

### P1-15 · 设备私钥明文落盘、目录权限过宽

`DeviceIdentity` 把设备密钥以明文 base64 写在 `device.key` 里，且不设权限。
R-01 明确要求"禁止落盘明文"。

## 3. 平台与 portal 侧的系统性缺口（已修复）

| 缺口 | 后果 | 修复 |
|---|---|---|
| 没有任何"自然人"账号的创建途径 | 所有人工事务端点在真实部署里**不可达** | 启动时用 `HARNESS_HUMAN_*` 引导第一个控制台账号 |
| `/policy/check` 的 `contentTrust` 缺省为 trusted | 省略字段即拿到可信通道 | 改为**必须显式声明**，否则 400 |
| 终端静默 15 分钟不会自动降权 | R-01 / A0-6 只在文档里 | 定时作业把静默终端置 `offline`，策略层对离线终端拒绝写操作 |
| 超时审批不会自动过期 | 待办里堆着一排永远 pending | 定时作业自动过期 |
| Kill-Switch 的"终端"粒度匹配不上 | 第 5 个粒度是摆设 | 策略请求现在带 `terminalId` |
| 拒绝的治理动作不留审计 | "谁尝试过越权"查不到 | 生命周期非法迁移、TTL 超限等拒绝路径全部补审计 |
| portal 的 `/api/harness/**` 整个命名空间 404 | 平台侧接口全不可用 | `web.xml` 增加 filter 映射；按 `alwaysSelectFullNamespace=true` 拆成三个 package |
| portal 的配置文件路径错 + 初始化时机错 | 命名空间永远是 503 | 路径改 `/WEB-INF/props/...`；改为首次请求时惰性加载 |
| portal 验签后没有把请求体回填 | 所有 POST 收到空参数 | 安装缓存请求并解析 JSON 到 `harness.parameters` |
| portal 先占用 nonce 再验签 | 攻击者可以烧掉合法客户端的 nonce | 改成**验签通过后**才占用 |
| portal 只有 2/6 条登录路径拒绝数字员工 | A0-2 的"全部失败"不成立 | 6 条凭据查询全部加 `isAI=0`；`isAI` 查询失败改为**失败关闭** |
| `blast_radius` 是 TINYINT，种子值 1000 被截断成 127 | 最高风险能力的"影响半径"是错的 | V6 改成 `INT` 并恢复种子值（真实 MySQL 8 已验证） |
| 跨系统 HMAC 靠人工脚本比对 | 已经漂移过一次 | `verify-portal-interop.sh` 现在自动编译并比对**三方**（portal / platform / terminal）签名 |

## 4. 终端：两个东西，两套实现

评审时仓库里有**两个**终端，都不成立：

* `harness-terminal/`（Rust，根目录）：不在任何构建里、无任何引用、**编译不过**
  （`Cargo.toml` 缺 `pymysql`/`rand`/`hmac`/`sha2`；代码用 clap 3 的 `App`，依赖声明的是 clap 4；
  `matches.is_present("install")` 引用了未定义的参数会 panic）。
  它直连 MySQL、用 root 账号、口令硬编码在源码里，自己往库里写绑定码——这与
  "终端不碰业务库、绑定码由平台签发、终端只走 HMAC 服务账号"整套设计相反，
  而且绕开了吊销与审计。它查的 `harness_terminal` 表还有两列在 03 §2.1 的 DDL 里并不存在，
  连库名（`harness_terminal` vs `harness`）都不一样。

* `harness/harness-terminal`（Java，harness 工程内）：设计上是终端设备外壳的正确位置
  （README 明确"protocol 会被原样嵌进终端运行时，一份代码三平台分发"），
  但只有 3 个类、**不在 reactor 里**、没有 `TerminalMain`（shade 插件指向的主类不存在），
  `LocalPolicy` 构造即崩。

现在这两个位置各归其位：

### 4.1 `harness/harness-terminal`（Java）= 设备外壳

* 设备身份（重启不变、密钥 0600、不写明文口令）
* 平台客户端（HMAC 签名与平台逐字节一致，有跨模块互认测试）
* 绑定码流程（`hello` → 平台发码 → 自然人在控制台输入 → `bind`）
* 心跳循环 + 被吊销时立即放弃能力
* 本地拒绝策略（能力 / 等级 / 路径白名单 / 审批令牌 / 审批范围绑定）
* CLI：`install / status / hello / bind / heartbeat / run / revoke`
* 可执行产物：`harness-terminal-0.1.0-SNAPSHOT.jar`（自包含，80 KB）

### 4.2 `harness-terminal/`（Rust）= 终端智能体运行时

这一版是**重写**的，不是修补——原来的代码没有一行能复用。它现在是一个完整的 coding agent：

| 要求 | 实现 |
|---|---|
| 收集上下文 | `workspace.rs`：遍历工作区、识别 40+ 种语言、按语言与体积统计、忽略噪声目录；`agent::build_context_packs` 按任务关键词把相关文件打进预算内的上下文包 |
| 采取行动 | `tools/`：`read_file` / `write_file` / `edit_file`（精确替换，**不唯一就拒绝改**）/ `delete_file` / `list_files` / `search_code` / `shell_exec` / `run_tests` / `git_status` / `git_commit` |
| 验证结果 | 工具返回**原样**输出（编译错误、测试输出、diff），`run_tests` 额外抽出失败用例摘要 |
| 自主循环 | `agent/mod.rs`：`模型 → 工具调用 → 策略检查 → 执行 → 结果回灌 → …`，带步骤预算与上下文预算，产出 `TaskOutcome` 与可回放的 transcript |
| 扩展（skill/MCP） | `skills/mod.rs`：SKILL.md + frontmatter + scripts/，**坏 frontmatter 报错不忽略**；`mcp/mod.rs`：stdio JSON-RPC 客户端（`initialize` → `tools/list` → `tools/call`） |
| 多模型 | Anthropic Messages API / OpenAI chat-completions / `ScriptedModel`（离线回放，测循环用） |
| 直接操作与执行 | 编辑文件、创建 git 提交、运行测试与 shell 命令 |

**和普通 coding agent 的区别是它受治理约束**：每次工具调用先过 `policy::LocalPolicy`
（能力 / 自治等级 / 路径白名单 / 绑定到命令与路径的人工审批令牌）。平台被攻破、边缘层撒谎、
工具参数被投毒，都绕不过本地的拒绝规则。技能与 MCP 是**内容**不是授权：MCP server 不能自授能力。

构建：`cargo build --release`（7.2 MB 单二进制），`cargo test` → **38 tests 全绿**。
命令行：`run` / `inspect` / `tools` / `replay`。

**仍然缺**：03 §3 的 TCP 帧通道与边缘层（平台目前只有 HTTP）；MCP 工具目前只注册进目录、
实际调用要由会话发起；本地模型（Qwen3.8B）尚未接入。

## 6. 待决事项

1. **Rust `harness-terminal/`** 已按"终端智能体运行时"重写（38 tests），不再是孤儿工程；
   但它与 Java 设备外壳之间**还没有接线**——外壳负责身份与心跳，智能体负责干活，
   两者应当共享同一份能力集与审批令牌（目前各有一份 `LocalPolicy` 实现）。
2. **A0-10 的口径**：portal 侧 21 处改动是否接受？其中 10 处修改的是既有文件。
   如果"≤8 处、全部新增"是硬约束，需要换一种实现 A0-2 的方式（例如在 `Users.hbm.xml`
   层面做映射，而不是在 6 处 DAO 里加条件）。
3. **E-01 / E-05 两个 errata 仍需设计方确认**：去重窗口粒度、帧 MAC 覆盖范围。
4. **注入检测器**是当前唯一还开着的"读到的内容当指令"缺口，建议作为下一批的第一项。
