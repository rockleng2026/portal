## 0. 阅读指南与本文档的立场

本文不是功能愿望清单，而是**可施工的设计**。所有机制都必须回答三个问题：

1. **谁授权？**（授权链：自然人 → 岗位 → 数字员工 → 工具 → 设备）
2. **失败了怎么办？**（可回滚、可归因、有人负责）
3. **凭什么相信它做对了？**（证据：日志、评测、影子对比、审批痕迹）

设计立场（贯穿全文，也是"对抗思路"的正面表达）：

| # | 立场 | 反面（我们要主动否决的做法） |
|---|------|---------------------------|
| P1 | **自主性必须分级授权**，不是"给不给 AI 权限"二选一 | 一次性给全套权限、靠 prompt 约束 |
| P2 | **AI 不能给自己授权**。审批链上必须存在自然人锚点 | AI 审批 AI、AI 自我提权 |
| P3 | **AI 员工是组织里的一个岗位**，不是一个外挂机器人 | 在 portal 之外另建一套"影子组织"，与真实组织脱节 |
| P4 | **每次自主动作都留痕**，可回放到分钟级 | 只留最终结果日志 |
| P5 | **可逆优先于高性能**：任何不可逆动作先影子跑 | 直接对生产库做自主写操作 |
| P6 | **记忆即代码**：经验体/技能必须版本化、签名、可回滚 | 让模型自由改写自己的长期记忆 |
| P7 | **联邦即边界**：跨组织互联默认不信任 | 互联即全互信 |
| P8 | **可退役**：每个数字员工有明确的退出与移交路径 | 只进不出，永久占用算力 |

## 1. 目标与非目标

### 1.1 业务目标（承接原始诉求）

- **G1 数字化转型基座**：让"数字员工"作为正式员工进入现有企业组织，承接真实工作流，而不是聊天机器人。
- **G2 真干活**：AI 员工必须能**操作真实系统**（工单、订单、项目、代码、服务器、日志），产出可验收的交付物。
- **G3 低接入成本**：新接入一套业务系统（OpenAPI/MCP/数据库只读视图）的工作量以**人日**计，而不是以月计。
- **G4 降本增效**：单台数字员工节点（5090 主机）约 5 万元硬件 + 450 元/月电费，年化约 10.4 万元；必须能算出它替代/辅助了多少人力工时。
- **G5 FDE 可交付**：方案能落到任意行业企业（FDE = Forward Deployed Engineer），交付物标准化。

### 1.2 明确非目标（Non-Goals，写下来防止范围蔓延）

- **N1** 不重建 portal 的 OA 能力。任务/日程/项目/消息/日志/组织全部**复用** portal 现有模块。
- **N2** 不在 portal 老框架里塞新代码主体。数字员工管理平台**独立部署、独立演进**，只通过薄适配层读写 portal。
- **N3** 本期不做"全自动无人审批"。任何涉及生产数据变更、资金、对外发送的动作，**必须有人类审批锚点**。
- **N4** 本期不做跨企业的**数据业务流**互联，只做**能力与任务的受限联邦**（见 §11.3）。
- **N5** 不承诺"零幻觉"。承诺的是"错误可发现、可拦截、可归因、可回滚"。

## 2. 现状勘察（设计的事实基础）

设计必须建立在 portal 的真实结构上，而不是想象的 OA。

### 2.1 组织与权限骨架（可直接复用）

| 表 | 关键字段 | 在 harness 方案中的角色 |
|---|---|---|
| `department` | `id, name, parentId, directorId, depNo, gradeid, filialemark, fiiale` | **组织树**。数字员工挂靠到某个部门节点，`directorId` 即数字员工的汇报对象 |
| `department_grade` | `dg_num 1..7` | 部门层级，决定升级/越级审批的路径长度 |
| `employee` | `id, uuid, name, department, position, workposition, gradeid, isLeave, isLoginAccount, approvemoney, email, Tel, empNo, photo` | **数字员工的物理身份载体**。AI 员工在 `employee` 里有一行，因此天然出现在组织树、通话录、统计里 |
| `employee_grade` | `grade_num 1..11` | 员工层级 |
| `workposition` | `id, name, deptid, workgrade(1..5), workcontent, functionIDs, permissions, parpostionid, ispersonman` | **岗位即职责即权限**。`functionIDs` 授权菜单，`permissions` 授权到 `funcID.subID` 粒度。这是"岗位重新设计"的天然载体 |
| `workposition_employee` | 岗位↔员工多对多 | 一人多岗 |
| `roles` | `RoleID, SuperID, roleName, functionIDs, permissions` | 角色权限集，`permissions` 形如 `351.7,352.1` |
| `role_function_info` | `UserID, functionIDs, permissions` | 个人级权限覆盖（优先于角色） |
| `functioninfo` | `FunctionID, SuperID, linkFunctionName, linkFunctionPage` | 功能/菜单树。权限判定靠 `linkFunctionPage like '%dourl%'` 反查功能 ID |
| `groups` + `user_group_info` | `groupID, groupName, superGroupID, permissionGrade, grade` / `userID, groupIDs, supergroupIds, resourcePermission` | **权限等级组**（`employee.position` → `groups.groupID`，见 `FK_employee_group` 索引）+ 资源可见范围。注意：`groups` 是 MySQL 8 保留字，Hibernate 映射需反引号（见 `Groups.hbm.xml`） |

> **关键结论 A**：portal 的权限模型是 **"菜单功能 ID + 子操作位"** 的双层字符串模型。这意味着数字员工要"能干什么"，最自然的表达就是**给它一个 `workposition`（岗位）**，而不是自己发明一套 RBAC。岗位 = 职责描述（`workcontent`）+ 权限集（`functionIDs`/`permissions`）。这样"部门主管对员工岗位重新设计和定位"（原始诉求）天然落地为**修改 `workposition` + 重新绑定 `workposition_employee`**，且历史版本可追溯（harness 侧留快照）。

> **关键结论 B**：`LoginInterceptor`（`src/com/fuao/fajxc/interceptor/LoginInterceptor.java`）用 **Cookie(`loginName`,`password`)** 做身份识别，密码是 **可逆加密串**（`m7tTVEaMykg=`，`CipherUtil`/`MD5`），并用 `linkFunctionPage like '%dourl%'` 反查功能点做鉴权。这意味着：
> - 数字员工**不应该**复用 Cookie 会话去模拟真人登录 —— 一旦泄漏即等同真人失窃。
> - 权限判定是**基于 URL 路径**的，所以新增任何 API 端点，如果不登记 `functioninfo`，就会绕开权限体系（要么全开、要么全关）。**harness 的 API 必须在 `functioninfo` 登记并走独立拦截器栈**，这是硬性工程约束。

### 2.2 业务工作流骨架（数字员工要"接"的东西）

| 能力 | 表 | 说明 |
|---|---|---|
| 待办/任务 | `mission`, `mission_emp`, `missiontype` | 任务主表 + 任务-员工多对多（`status`、`complete_describe`、`complete_fjbs`）。**这就是"待办"落点** |
| 计划/反馈 | `plans`, `missiontype` | 周期计划与反馈 |
| 日程 | `scheduleplan` | `plantype` 0日/1周/2月/3季/4年，`remindtime`、`sendStyle`(系统消息/短信/邮件)、`remainSet`、`importantLevel`、`participator`、`organizer`、`taskid` |
| 项目 | `new_project`, `new_function`, `new_task`, `new_prjtresource`, `new_approve`, `new_participator`, `new_problem`, `new_question`, `new_historyquestion`, `projectemp`, `projectlead`, `projectemplead` | 完整项目树：项目→功能→任务→资源消耗→审批→参与人→问题→历史。`new_prjtresource.appstatus`(0未通过/1通过/2审批中) 与 `new_question.handlestatus`(0未提交/1未反馈/2已反馈) 是天然的审批/反馈状态机 |
| 站内信/IM | `message`, `messagereceiver`, `messagehistory`, `messagetype` | `sender`/`sendertype`/`messagetype`/`priority`；`message.superid` = **回复父 ID**（`MessageAction` 中 `from Message where superid=...`）；接收端有 `readfalg`/`delfalg`/`planid`（可挂日程）。**注意：portal 没有"群聊成员表"** —— 群组语义由 `groups` + `user_group_info.groupIDs` 承载，harness 侧需自建会话-成员索引（见 `03` §2.6） |
| 工作日志 | `worklog` | `empId, recordTime, workresult, content, selftemper, suggestion, type(0日志/1周志), replier, replyTime, replyContent, isView(0未批注/1已批注/2已查看)` |
| 公告 | `notice`, `notice_dept` | `audtitingFlag`(0未审/1通过/2失败/3撤销/8已接收) |
| 故障工单 | `conkout`, `conkoutask`, `questioncategory` | 售后故障流转：`State` -1退回/0初始/1接收/2转接/3处理/4完成/5评价 |
| 销售线索 | `intentfollow_up` | 销售意向跟踪 |
| 审批流 | `auditingordertab`, `approverecord`, `new_approve` | `auditingordertab.handlestate`(0未审/1审核中/2已审)、`mark`(1=他审完他人免审；2=他人也须审) |
| 操作日志 | `executerecord` | `empId, content, executeTime, entityId, entityName, seenEmpId` —— **自主修复的取证数据源** |
| 服务器/监控 | `servermonitor`, `upserver`, `addserver`, `t_logtab`, `cdn_logs` | 运维侧数据源 |
| 知识库 | `knowledgelib` | `libType, libTitle, libContent, libAccessory, empid` |
| 资源审批 | `t_resourcecheck` | `isstate`(0未审批/1已审批/2已回复) |

> **关键结论 C**：portal 已经具备"任务 → 审批 → 反馈 → 日志 → 评价"的完整闭环。数字员工**不应该另建任务系统**，而应该以 `employee` 身份 + `workposition` 权限去操作这些既有表。这样做的收益是：领导在 portal 里看到的"每个员工正在干的活"，天然就包含数字员工；不需要做双向同步。
> **代价**（必须在方案里正面承认）：portal 的表是 2011–2016 年的设计，多处用 `varchar` 存 ID 列表（如 `workposition.functionIDs` 是逗号分隔字符串）、`varchar` 存时间（如 `worklog.recordTime`）、表引擎混用 InnoDB/MyISAM、字符集 `utf8_general_ci`。**harness 侧不复制这套坏味道**，采用自己的规范化库，通过适配层做映射。

### 2.3 反向结论：不要在 portal 里改的东西

- 不改 `LoginInterceptor` 的核心判定逻辑（影响面 497 个功能点、风险极高）。改为**新增一个独立命名空间的 API 拦截器**（`/api/harness/**`），走服务账号 + mTLS/签名，不与 Cookie 体系混用。
- 不在 `users` 表里复用真人密码存储方式给 AI 账号。AI 账号使用独立的 `harness_principal` 映射表 + 长随机密钥（不落 `users.password`）。
- 不动 `executerecord` 的写入语义（它被很多统计页依赖）。AI 员工的轨迹写在 harness 自己的库，同时**异步镜像**一条摘要到 portal 侧（可选）。

### 3.1 分层职责与"谁说了算"

| 层 | 拥有 | 不拥有 | 失效降级 |
|---|---|---|---|
| 终端层 | 设备控制、本地推理、工具执行、离线队列 | 业务决策、跨设备编排 | 断网 → 本地只读 + 排队，恢复后补传 |
| 边缘层 | 注册、心跳、指令路由、算力池、部署 | 业务语义、审批 | 中心不可达 → 终端降级为本地自治（仅 L0/L1 权限） |
| 信令层 | 消息路由、群组、@、离线推送、联邦网关 | 业务数据存储 | 不可用 → 邮件通道兜底 |
| 大脑层 | 系统级决策、最终裁决、跨系统管理、自我进化 | 直接持有业务数据写权限 | 大脑不可用 → 退化为"部门主管 + 预案"模式 |
| 平台层 | 生命周期、权限、审批、看板、发布、计量 | 模型推理 | 平台不可用 → 大脑可继续按缓存策略运行（只读） |
| 业务系统 | 事实数据、最终状态 | 决策 | —— |

**降级链是设计的一部分，不是故障预案的附注**：任何一层挂掉，数字员工必须降级为"可解释的保守行为"，而不是"乱动"。

## 4. 统一概念模型（ID 体系先定，否则互联必乱）

整个系统所有实体使用 **UUID v7（时间有序）作为主键**，与 portal 的 `int` 自增 ID 并存，通过映射表关联。

| 概念 | ID | 归属 | 说明 |
|---|---|---|---|
| 自然人 | `emp:{portal_employee_id}` | portal | 员工 |
| 数字员工 | `agent:{uuid7}` | harness | 有唯一 `agent_key`（如 `agent:leon:sales:sh001`） |
| 岗位 | `pos:{portal_workposition_id}` | portal | 数字员工在组织中的位置 |
| 终端 | `term:{uuid7}` | harness | 一台设备 = 一个执行体 |
| 设备-账号绑定 | `bind:{uuid7}` | harness | 绑定后该终端继承该账号在 portal 的权限 |
| 任务 | `task:{portal_mission_id}` | portal | 待办落点 |
| 事件 | `evt:{uuid7}` | harness | 触发源 |
| 指令 | `cmd:{uuid7}` | harness | 脑 → 终端 |
| 能力 | `cap:{uuid7}` | harness | 工具/MCP/OpenAPI/CLI 的统一抽象 |
| 技能 | `skill:{uuid7}@v{n}` | harness | 可进化、可签名、可回滚 |
| 经验体 | `exp:{uuid7}` | harness | 成功/失败片段（episodic memory） |
| 事件单 | `inc:{uuid7}` | harness | 问题/故障/需求单（对接 portal `conkout`/`new_question`） |

> **为什么必须是 UUID 而不是 portal 的 int ID**：harness 要支持"一个大脑一个数字员工"跨企业联邦，跨组织 ID 冲突是必然的；且终端在企业外网离线时也需要生成自增记录。

## 5. 组织与权限对齐

### 5.1 数字员工的"入职"流程

```
[管理平台] 创建 Agent 模板（角色/技能/岗位/权限/模型/预算）
      ↓
[管理平台] 分配终端（一机一人）→ 终端装机 → 绑定员工账号
      ↓
[适配层] 在 portal.employee 插入数字员工行（isLoginAccount=1, uuid=agent uuid）
      ↓        portal.users 插入对应登录名（AI 账号，密码走 harness 独立凭证体系）
      ↓        portal.workposition_employee 绑定岗位（权限来自岗位的 functionIDs/permissions）
      ↓
[门户] 数字员工出现在组织树 / 通讯录 / 任务接受人下拉 / 日程参与人 / 领导评价
      ↓
[终端] 首次上线 → 拉取自身权限快照 → 注册到边缘层 → 开始接收事件
```

### 5.2 权限三层模型

数字员工的实际权限 = **能力(capability) ∩ 作用域(scope) ∩ 时效(TTL)**，三者缺一不可。

- **Capability**：工具级。`cap:portal.task.complete`、`cap:ssh.exec`、`cap:file.write`、`cap:mcp.gitlab.*`。每个能力声明：可读/可写、是否可逆、影响半径、所需审批等级。
- **Scope**：数据级。绑定到 `agent` + `department` 子树 + `resourcePermission`（复用 portal `user_group_info.resourcePermission` 的语义）+ 可选的数据行级过滤（如"只看自己部门的工单"）。
- **TTL**：时效级。能力授予带过期时间；自主提权授予的能力 **TTL ≤ 24h** 且**到期自动降权**。

### 5.3 自主等级（Autonomy Level）

这是整个方案最重要的治理旋钮。

| 级别 | 名称 | 允许的自主行为 | 典型角色 |
|---|---|---|---|
| **L0** | 观察 | 只读、只报告、不写任何系统 | 刚入職的新员工、审计专用 |
| **L1** | 建议 | 产出建议/草稿，需人工执行 | 售前方案、UI 草图 |
| **L2** | 执行-低风险 | 可写低风险目标（如自己名下工单状态、草稿、测试环境） | 售后工单流转、测试用例 |
| **L3** | 执行-中风险 | 可写生产但需**事后报备**（可回滚） | 代码提交到特性分支、测试环境发布 |
| **L4** | 执行-高风险 | 可写生产且不可回滚（如生产库 DDL、对外邮件、资金） | **默认禁用**；仅在有明确白名单 + 双人审批 + 影子验证后按单次任务临时开启 |

**降级默认生效**：Agent 连续出现低级错误、审批驳回率升高、模型置信度下降时，平台自动降级其自治等级（见 §14.4）。

### 5.4 汇报关系（"责任范围内自己负责，其他向领导汇报"）

- 数字员工的**汇报对象**由 `portal.department.directorId` 自然导出。
- **责任范围**由 `workposition.workcontent`（工作职责文本）+ `workposition.functionIDs`（可操作功能）共同界定。
- 当事件超出其岗位 `functionIDs` 范围时，**不得自行处理**，必须：
  1. 生成 `escalation` 事件，路由到 **直属上级岗位**（数字员工或真人）；
  2. 若上级也是数字员工且同样越权，**向上最多 2 级**，之后必须转真人；
  3. 若涉及项目管理方（`new_project.approver` / `projectemp.leadname`），并行通知。
- 每次升级都写入 `harness_escalation`，形成"AI 员工工作轨迹"。

> **反直觉但必要的设计**：**不允许 AI 无限级联上报**。第 2 级之上必须转真人，否则会出现"AI 之间互相甩锅、无人负责"的组织熵。这条在 `02-对抗评审.md` R-06 展开。

## 6. Agent 双态模型

原始诉求："管理态（设计/UI/开发/测试/运维 agent）"与"用户态（对用户提供 AI 助理，默认名 leon）"。

### 6.1 双态定义

| | **管理态 (Management)** | **用户态 (Service)** |
|---|---|---|
| 面向 | 平台管理者、部门主管、流程负责人 | 最终业务用户、领导、协作方 |
| 职责 | 设计/UI/开发/测试/运维；定义标准、评审产出、承接用户态上报 | 直接服务用户：答疑、办事、跟进、汇报、派工 |
| 典型交互 | 看板上操作、审核问题单、编排方案小组、发布与灰度 | IM 私聊、群内 @、待办处理、邮件 |
| 默认名 | 按职能命名（架构师/UI/开发/测试/运维） | **leon**（可改） |
| 权限倾向 | 高权限、强审计、批量操作 | 低权限、窄作用域、用户可见 |

### 6.2 两态之间的关系：一个"服务总线 + 审核闸门"

```
用户态 Agent（leon）
   │  用户提问 / 用户发现问题 / 用户态自己巡检发现问题
   ▼
[问题采集] → 生成 issue_draft（分类、影响面、复现证据、建议动作、所需权限）
   ▼
[管理态 Agent 审核]
   ├─ 判定：不是问题 → 【打回】，必须写驳回意见（理由、依据、期望改进）→ 回流用户态 → 关闭或转为建议
   ├─ 判定：是问题 且 动作在能力范围内 且 L≤2 → 【受理-自助修复】→ 记录 → 通知用户态与相关人
   ├─ 判定：是问题 且 动作需更大权限 → 【提权申请】→ 生成 capability grant 请求（TTL、作用域、影响面、回滚方案）
   │        └─ 自然人管理员审批（平台管理员/系统管理员岗位/部门主管，按影响半径定审批层级）
   │              ├─ 批准 → 授予临时能力 → 执行 → 撤销能力 → 归档报告
   │              └─ 驳回 → 回流用户态并说明原因
   └─ 判定：是问题 但 影响面超出判断能力 → 升级到专家 Agent / 项目管理方 / 真人
```

**状态机（`harness_issue.state`）**：

```
draft → submitted → reviewing → [rejected | self_fixed | approval_pending | escalated | fixed]
  ▲        │           │            │                                        │
  └────────┴───────────┴────────────┴────────────── replan ◄────────────────┘
```

`rejected` 必须携带 `reject_reason`（非空约束），且必须回传给用户态 Agent —— 这条是"管理态可以审核、不是问题的打回、给出拒绝意见"的落地。

### 6.3 "Agent 可自定义 + 拉入组织结构"

- 管理后台提供 **Agent 模板市场**（内置：售前顾问/售后工程师/软件工程师/助理小C/市场分析师-佳琦/UI 设计师/测试工程师/运维工程师/数据分析师/项目管家）。
- 用户可基于模板创建：改名字、头像、岗位绑定、技能包、模型、预算、自主等级上限、可见范围。
- **"拉入组织结构"** = 一次操作同时完成三件事：① 写入 `portal.employee`（成为一个员工）；② 绑定 `portal.workposition`（获得岗位权限与汇报关系）；③ 在 harness 侧建立 `agent ↔ terminal ↔ scope` 绑定。**必须是一个事务**，避免出现"在 harness 里存在但 portal 里查无此人"的幽灵员工。
- 反向：**不允许**把一个 Agent 拉入与其岗位 `deptid` 不匹配的部门（除非显式授权跨部门，并标注"支援"关系）。这与 portal 现有的 `department.directorId` 语义冲突时会报错。

## 7. 核心大脑 Harness（Core Brain）

大脑是**系统级、最终决策**的所在，职责五项：

### 7.1 决策与裁决

- **决策对象**：跨 Agent 冲突（两个 Agent 对同一问题给出相反处置）、跨系统动作（一次变更同时影响 portal + CDN + 进销存）、跨组织联邦请求。
- **裁决原则（写进决策记录）**：① 权限优先于效率（越权请求一律拒绝并升级）；② 影响半径优先于收益；③ 可回滚优先于不可回滚；④ 岗位责任优先于任务紧急度（谁负责谁签字）；⑤ 有人在场优先于无人值守。
- **裁决记录**：`harness_decision` 表必须包含：冲突双方主张、适用原则、裁决结果、被驳回的方案、裁决者（大脑 or 自然人）、可回滚性评估。**不记录理由的裁决不允许执行。**

### 7.2 模型推导

- 大脑不直接持有业务数据连接，只持有**元数据 + 能力索引**；具体数据由执行该能力的 Agent 拉取并摘要回传（最小暴露原则）。
- 推理分层：**快思考**（规则/状态机，毫秒级，用于 L0/L1 判定、告警分级）→ **慢思考**（LLM 推理，用于方案生成、异常归因、跨任务规划）。
- **快慢分离**是成本控制的主杠杆：绝大多数日常事件走规则路径，不烧 token。

### 7.3 分析与控制

- **预算控制**：每个 Agent / 部门 / 全局三级 token+算力预算；超限自动降级到本地小模型或排队。
- **熔断**：单位时间失败率/误报率超阈值 → 自动暂停该 Agent 的自主执行 → 通知管理态 → 生成报告。
- **节流**：告警风暴去重与抑制（相同指纹的异常在时间窗内合并为一条，附计数）。

### 7.4 跨系统管理

- 统一**业务系统注册表** `harness_system`：每个系统记录其类型（portal/CDN/进销存/外部）、接入方式（DB 只读视图 / OpenAPI / MCP / CLI）、能力清单、数据分级、责任人、可用性。
- **所有系统接入必须经过同一套接入工具**（见 §9），不允许"某团队私下写脚本连库"。

### 7.5 跨 Harness 交互

- 大脑作为**联邦根/成员**参与多组织协作（见 §11.3）。

## 8. 核心大脑与 Agent 框架

### 8.1 Claude Code / Claude 强点整合与 Agent 框架

为了满足"自主接收指令、自主开展工作、自我进化"的核心诉求，我们吸收了 Claude Code、Claude 以及其他主流 AI 编程助手的优点，构建了一个**标准化 Agent 框架**，所有数字员工均基于此框架实现。该框架不仅适用于代码生成类任务，也适用于各类业务自动化场景。

#### 8.1.1 Claude Code / Claude 关键优点提炼

| 优点来源 | 具体优势 | 在 harness 中的对应实现 |
|---|---|---|
| Claude Code / Claude | 多轮对话上下文保持精准，能够理解复杂的代码库结构和业务逻辑 | **上下文管理模块**：Agent 持有 `context_window`（基于 UUID 语境标识），对每一次交互进行结构化摘要，避免信息丢失 |
| Claude Code / Claude | 强大的工具使用能力（读取文件、运行命令、网络请求） | **工具调用规范**：统一 `harness_capability` 体系，其中 `kind=cli` 的能力直接对应 Claude Code 的工具使用模式，所有工具调用必须经过 `source_ref` 引用校验 |
| Claude Code / Claude | 能够生成完整的、可执行的代码片段并自测 | **技能（Skill）模板**：每个 Agent 可注册多个 `harness_skill`；技能包含 `definition.steps[]`（可执行步骤）、`definition.tools[]`、`definition.preconditions[]`、`definition.postconditions[]`，实现可签名、可回滚的自动化任务 |
| 主流编程助手 | 代码重构、重构建议、Bug 定位 | **经验体（Experience）积累**：Agent 执行任务后，将`trajectory`、`outcome`、`context_hash` 写入 `harness_experience`，形成可检索的知识库，后续类似任务可直接复用 |
| 主流编程助手 | 多语言支持（Python, JavaScript, Java, Go 等） | **语言无关**：Agent 框架完全语言无关，通过 `capability` 的 `input_schema`/`output_schema` 定义数据结构，而非代码字符串 |

#### 8.1.2 Agent 框架核心组件

每个数字员工 Agent 实例包含以下核心模块：

1. **感知层 (Perception)**
   - 从事件总线接收 `harness_event`
   - 内容提取：仅提取 `payload.extracted.fact`，标记 `content_trust=untrusted` 的内容只能作为事实库使用，不能直接作为参数
   - 指令注入检测：对 `payload.extracted.intent` 进行祈使句/越权词模式匹配，命中则降级为 L0 并告警

2. **推理层 (Reasoning)**
   - **快思考**（规则/状态机，毫秒级）：处理 L0/L1 级别的判定、告警分级、简单的工具选择
   - **慢思考**（LLM推理，秒级）：用于方案生成、复杂规划、跨任务协调。由大脑层统一调度，避免每个 Agent 自行调用大模型

3. **计划层 (Planning)**
   - 生成 `harness_plan`：目标 `goal`、步骤 `steps[]`（`seq, action, cap_id, args, acceptance, rollback`）
   - **里程碑**：每个步骤必须有 `acceptance`（验收标准）和 `rollback`（回滚方案）

4. **执行层 (Execution)**
   - 调用 `harness_capability` 中注册的工具（CLI/MCP/OpenAPI/DB/HTTP）
   - 所有参数必须带 `source_ref`（引用不可信来源时必填），否则被拦截
   - 结果回传：`harness_action` 记录 `arguments, arguments_hash, result, exit_code, status`

5. **回顾层 (Retrospect)**
   - 任务结束后自动生成 `harness_experience`
   - 提取 `verdict`（success/failure/rejected/rolled_back/complained）、`confidence`、关键`trajectory`片段
   - 经验体可被其他 Agent 通过 `harness_skill` 复用或评测

### 8.1.3 五个能力点在 Agent 框架下的实现

#### 8.1.3.1 自发工作（Proactive Work）

**基于 Agent 的目标调度器**：
- 每个 Agent 持有 `goal_set`：由 `workcontent` 派生的长期目标 + 周期目标 + 改进目标
- **优先级评分**：`score = 业务价值 × 紧迫度 × 置信度 × 无人可做系数 × Agent_能力系数`
- `Agent_能力系数` 来源于 Agent 已注册的 `harness_skill` 丰富度和 `confidence` 历史记录
- **无人可做系数**：该事项在组织内没有自然人负责且没有其他 Agent 承诺 → 系数高
- Agent 不得主动发起对外承诺（报价、合同），所有此类动作需 `requires_human=true`

#### 8.1.3.2 自主接收指令（Trigger Matrix）

触发源与接入方式保持不变，但执行流程更新为 Agent 框架流：

| 触发源 | portal 落点 | 接入方式 | Agent 流程 |
|---|---|---|---|
| 领导邮件安排 | 邮件系统 / `sendmessage` | IMAP/SMTP 监听 | 1. 事件进入 `harness_event` 
2. 感知层提取 `extracted.intent` 
3. 推理层快速判定意图类别
4. 计划层生成 `harness_plan`（带 acceptance + rollback）
5. 执行层按 plan 逐步调用 capability
6. 结果回传至 `harness_action`，感知层标记 `content_trust` |
| 聊天对话安排 | `message` + `messagereceiver` | 消息 API 订阅 + 信令推送 | 同上，优先由用户态 Agent（leon）处理，若越权则路由至管理态审核 |
| 群里的 @ | `message.superid` 会话 + 正文 `@xxx` | 同上 + 解析器 | 同上，@ 后的对象若为 Agent 则直接派发；若为人员则生成 issue_draft |

#### 8.1.3.3 自主开展工作（Autonomous Work）

**Agent 执行流程**：
1. **计划生成**：Agent 基于 `goal_set` 和当前上下文生成 `harness_plan`
2. **步骤拆解**：计划被拆解为 `steps[]`，每个步骤对应一个 `capability` 调用
3. **能力授权**：每一步的 `cap_id` 必须在 `harness_grant` 中查询有效授权
4. **工具调用**：执行 `CLI`/`MCP`/`OpenAPI`/`HTTP` 等能力
5. **结果验收**：若 `result` 满足 `acceptance` → 标记步骤完成；否则触发 `rollback` 计划
6. **汇报**：执行结束后，自动生成 `harness_experience` 并写入日志

#### 8.1.3.4 自我进化（Self-Evolution）

**经验体 → 技能 → 发布流水线**：
1. **经验采集**：任务结束后，系统自动生成 `harness_experience`（`outcome`、`confidence`、`trajectory`）
2. **候选技能**：基于经验体，系统生成候选 `harness_skill`（`definition.steps[]`、`definition.tools[]` 等）
3. **评测**：在 `harness_eval_set` 中进行回放测试（`replay`/`sandbox`/`adversarial`），生成 `eval_result`
4. **人工/自治评审**：
   - 评审通过 → 标记 `status=released`，Agent 可在任务中直接调用
   - 评审未通过 → 标记 `status=rolled_back`，经验体保留但技能不发布
5. **灰度发布**：新技能先在 1-3 台终端灰度运行，观察 72h 无误才全量发布
6. **版本回滚**：任何已发布的技能可在 5 分钟内回滚到上一版本

#### 8.1.3.5 方案制定小组（Expert对抗评审）

**通用化的“对抗讨论”逻辑**：
- **新建方案制定小组**：针对一个议题，邀请 N 个专家（可为具备不同领域技能的 Agent 或真人）
- **对抗讨论流程**：
  1. 每个专家独立给出方案（`A-方案`, `B-方案`）
  2. 系统将两个方案置于同一上下文，进行对抗讨论
  3. 系统基于 `principles_applied`（原则编号 P1-P8）进行打分和逻辑分析
  4. 综合得出最终方案 + 每个人的"评审意见"（同意/有条件/反对 + 见解）
  5. 所有意见写入 `harness_decision`，形成完整的"落款评审记录"
- **通用化实现**：该逻辑不依赖具体领域，通过`topic`、`context`、`principles_applied`、`outcome`三元组即可任意主题实现
- **应用场景**：产品需求评审、技术方案评审、自主修复方案评审等

## 8. 自主运行的五个能力点

原始诉求的五点，逐条给出机制。

### 8.1 自发工作（Proactive Work）

不是"等派活"，而是**基于岗位目标主动产出**.

- 每个 Agent 持有**目标集 (goals)**：由岗位 `workcontent` 派生的长期目标 + 周期目标（如"本周完成 5 个客户回访"）+ 改进目标（来自主管谈话结论）。
- **调度器**按优先级评分触发：`score = 业务价值 × 紧迫度 × 置信度 × 无人可做系数`。
- **无人可做系数**：该事项在组织内没有自然人负责且没有其他 Agent 承诺 → 系数高。这保证"数字员工填补真空"，而不是和真人抢活。
- **禁止项**：Agent 不得主动发起对外承诺（报价、合同）、不得主动变更生产、不得主动删除数据。所有此类动作需在事件类型上打 `requires_human`。

### 8.2 自主接收指令（Trigger Matrix）

| 触发源 | portal 落点 | 接入方式 | 延迟要求 |
|---|---|---|---|
| 领导邮件安排 | 邮件系统 / `sendmessage` | IMAP/SMTP 监听 | ≤ 60s |
| 聊天对话安排 | `message` + `messagereceiver` | 消息 API 订阅 + 信令推送 | ≤ 5s |
| 群里的 @ | `message.superid` 会话 + 正文 `@xxx` | 同上 + 解析器 | ≤ 5s |
| 定时的工作 | `scheduleplan.remindtime` / `plans` | 定时器 + portal 日程同步 | ±30s |
| 代办 | `mission_emp` | portal 任务 API 轮询(长轮询/WebHook) | ≤ 30s |
| 进行中工作巡检 | `mission_emp.status` / `projectemp.prjempplan` | 定时巡检任务 | 5–30 min |
| 临时触发（告警/异常） | `servermonitor` / `cdn_logs` / `t_logtab` / `executerecord` | 日志采集 + 规则引擎 | ≤ 10s |
| 上级评价/驳回 | `worklog.replier` / `new_prjtresource.appstatus` | 变更订阅 | ≤ 60s |

**统一入口**：所有触发都先落 `harness_event`（事件总线），再由路由器分派到 Agent 的 `inbox`。事件有**去重指纹**（`harness_event.fingerprint` + `event_window` 唯一键），避免重复处理。

**"临时触发快速处理"**：区分 `latency_class`：`realtime`（≤5s，走快思考）/`nearline`（≤60s）/`batch`（定时）。临时事件若在 SLA 内无法完成，**必须先回执"已接收，预计 X 时间"**，而不是静默丢弃。

### 8.3 自主开展工作（Execution Loop）

```
触发 → 理解(意图/实体/约束) → 制定计划(Plan) → 拆解任务(Subtask) → 分派
     → [可分派的分派给下级/同级 Agent 或建议给人] → 执行 → 校验 → 汇报 → 交接
```

- **自己写计划**：`harness_plan`（目标、步骤、依赖、验收标准、回滚点、预估成本）。
- **安排其他人工作**：见 §5.4 汇报关系；分派时必须带**验收标准**和**截止时间**，并写入 `mission_emp`（真实进入 portal 待办）。
- **交接工作**：交接包 = 目标 + 已完成事实 + 未完成清单 + 已遇坑 + 建议下一步 + 引用的证据 ID。交接必须落 `harness_handover`。
- **发送邮件/问询进度**：`sendmessage` 走 portal 内部消息；对外邮件需 `requires_human` 或 L3。
- **问询进度**：对已分派任务，Agent 在 SLA 到期前主动 ping（`mission_emp.status` 未更新 → 发消息 → 升级）。

## 9. 需求 → 业务系统 / Tool 的自主生成

原始诉求："根据用户需求自主生成业务系统/tool/通过 OpenAPI 或 MCP 接入到 harness 进行管理"。

这是**三种不同风险等级**的事，必须分开：

### 9.1 类型 A：接入既有系统（低风险，优先做）

- **OpenAPI 接入**：填写系统描述 → 大脑生成 OpenAPI 规范草案 → 人工校验 → 注册为 `harness_system` + 一组 `cap` → 生成 MCP Server 包装 → Agent 即插即用。
- **MCP 接入**：MCP Server 天然提供 tools/resources/prompts 三类接口 → 直接映射为 capability。**MCP 是首选集成方式**，因为它已经把"工具"标准化了。
- **数据库只读接入**：注册只读视图 + 行级过滤 + 字段脱敏策略 → 生成查询工具。
- **产出物**：一个 `harness_connector` 记录 + 一个 MCP Server 容器 + 一份能力清单。

**验收标准**：新系统接入从"拿到文档"到"Agent 可用" ≤ 3 人日。

### 9.2 类型 B：生成 Tool（中等风险）

- 场景：需求频繁、现有系统缺一个动作（如"批量把工单打上某标签"）。
- 流程：需求单 → 大脑生成工具规格 → 在**沙箱**（影子库/影子 API）生成并测试 → 生成契约测试 → 评审 → 发布为 MCP tool（走 §11 发布流水线）→ 灰度。
- **禁止**：生成的 tool 不得直接获得生产写权限；首次运行必须是影子模式（只读比对）。

### 9.3 类型 C：自主生成业务系统（高风险，默认人审）

- 场景：新产品/新工具（原始诉求中"产品部门-收集意向研发产品"）。
- 流程：意向收集（`intentfollow_up`）→ 需求聚类 → 方案制定小组（§10）→ 架构草案 → **人工评审门（Go/No-Go）** → 生成代码（管理态开发 Agent）→ 测试（管理态测试 Agent）→ 影子部署 → 评审 → 上线。
- **自主生成的边界**：
  - 可以生成：原型、前端、内部工具、只读报表、脚本、SQL 视图、MCP Server。
  - 不可自主生成并上线：涉及资金/合同/对外服务/生产数据写入的系统。必须人工 Go/No-Go。
- **产物溯源**：生成系统的每一行代码必须带 `agent_id + plan_id + prompt_hash` 溯源标记，否则不予合入。

## 10. 方案制定小组（对抗式决策的通用化）

原始诉求：给定议题，A 给方案、B 给方案，对抗讨论后形成最终方案，各人落款评审意见。

### 10.1 编排协议（可复用的通用模式）

```
[议题] topic
   ↓
[召集] 依据 domain 检索/指定专家 Agent（可含真人）
   ↓
[独立成案] 并行：每人独立提交方案 proposal_i（不互相可见，避免锚定）  ← 关键：独立性
   ↓
[交叉质询] 每人审阅他人方案 → 质疑点 critique_ij（必须针对具体条款）
   ↓
[对抗讨论] 轮次制辩论（建议 ≤3 轮），每轮输出立场修订
   ↓
[综合] 大脑（或主持人）合成 draft_final，标注每个争议点的取舍与依据
   ↓
[落款评审] 每个参与者独立签署 review_sign：同意 / 有条件同意 / 反对 + 意见  ← 记录进业务库
   ↓
[归档] 结论 + 反对意见 + 少数派立场 一并归档（禁止丢弃异议）
```

### 10.2 设计要点

- **独立性**：第一轮必须并行且互不可见（否则最强话术者主导全场）。这与"自我进化"里的"独立评测"同一原则。
- **落款不等于背书**：AI 落款记录的是"该 Agent 在此方案上的意见"，**不能替代自然人签字**。方案若涉及 L4 动作，**必须有人类签名**才可执行。
- **少数派意见必须留存**：归档结构包含 `proposals[] / critiques[] / rounds[] / final_draft / signoffs[] / dissent[]`。禁止只存最终结论。
- **反操纵**：方案小组的成员由大脑提议但由人确认（防止自选陪审团）。

## 11. 终端、边缘与联邦互联

### 11.1 终端安装包（Terminal Agent）

- 形态：Windows / Linux / macOS 三个安装包，**一份安装包 + 绑定码**，避免"每台机器编译一次"。
- 安装后：注册 Trinity 守护进程（开机自启、崩溃自拉、进程守护）、拉取自身配置、申请设备能力。
- **绑定即授权**：安装包首次运行生成 `device_id` + 一次性 `binding_code`；在管理平台输入绑定码并选择"绑定到哪个员工账号（自然人或数字员工）"；绑定完成后，该终端**继承该账号在 portal 的权限**并可执行该账号有权执行的动作。
  - **安全约束**：绑定后终端**不是**无限制控制权，而是"该账号权限 ∩ 终端设备白名单 ∩ 能力 TTL"。原始诉求说的"拥有这个设备的所有控制权限"，在本方案中收敛为"**该员工授权范围内的该设备控制权**"。这一收敛是必要的，理由见 `02-对抗评审.md` R-01。
- **基础工具包**：文件读写、Shell/PowerShell、浏览器自动化、HTTP、抓包/日志读取、数据库客户端、Git、压缩、截图、剪贴板、进程管理、截图 OCR。
- **本地模型**：Qwen3.8B（终端侧），承担：意图分类、敏感信息脱敏、本地摘要、低价值任务（如日志归并）。**大模型推理（云端满血版）只在大脑侧**。
- **经验体本地缓存**：本地保存近期经验/技能副本，断网时可用旧版技能；网络恢复后校验签名并更新。

### 11.2 蜂巢模式（Hive）

- **蜂王 (Queen)**：一个大脑实例（或指定的高阶 Agent）持有全局计划。
- **蜂群 (Swarm)**：终端 Agent 按能力标签被派发子任务。
- **协议**：
  - 蜂王只下发**任务契约**（目标 + 验收标准 + 约束 + 预算），不直接下发命令序列 → 保持终端的局部自主性。
  - 子任务在蜂群内**竞价/认领**（谁最适合谁接），避免蜂王成为瓶颈。
  - 每个子任务有**隔离沙箱**（独立工作目录/独立凭据/独立权限）。
  - 蜂王失效 → 蜂群进入**无主模式**：仅执行本地已授权的 L0/L1 动作 + 就地等待，不得各自为政继续派发。
- **熔断**：蜂王决策错误会被放大到全群 → 必须有"影响半径"上限（单次蜂王指令最多影响 N 个终端/或仅限某部门），并支持一键"蜂群静默"。

### 11.3 Trinity 守护进程

- 职责：进程守护、配置热更新、健康检查、本地队列、崩溃现场 dump、指标上报、**自我升级（受控）**。
- 安全：守护进程持有最高本地权限，因此**必须**：以独立低权用户运行 + 通过受限 sudo 规则提权（只允许白名单命令）、持有设备级密钥且密钥不可导出到业务进程、对自身升级包做签名校验。

### 11.4 IM 信令服务器与跨 Harness 互联

**信令服务器**职责：
- 长连接维护（WebSocket）、在线状态、消息投递、群组管理、`@` 解析与提醒、离线队列与重投、消息撤回（对应 `message.repealfalg`）、已读回执（对应 `messagereceiver.readfalg`）。
- **数据平面与控制平面分离**：信令只传消息与事件，不传业务大对象（大文件走对象存储 + 引用）。

**跨 Harness 联邦**（原始诉求："让不同用户部署客户端后让他们的 harness 来协同完成任务"）：

- **联邦模型**：每个 Harness 有 `federation_id`。互联通过**能力协商**而非全量互信。
- **协商内容**：`capability offer`（我提供什么能力、参数 schema、SLA、代价）、`capability request`（我需要什么）。
- **任务联邦**：A 组织的 harness 把一个**任务契约**（非数据）派给 B 组织的 harness；B 回传 `deliverable`（成果物 + 证据）。数据留在 B 侧，除非契约显式要求跨境传输且合规允许。
- **边界**：
  - 每个联邦关系是**显式授权**（管理员在管理平台点确认），不是自动发现即互联。
  - 跨境任务默认在**隔离工作区**执行，产出物需审核后才进入主系统。
  - 联邦身份用**短期能力令牌**（capability token，JWT，TTL ≤ 1h，scope 收敛到单任务），不用长期 API Key。
  - 全量审计 + 可吊销。

## 12. 看板体系（OPC 企业视角）

| 看板 | 使用者 | 数据来源 | 关键能力 |
|---|---|---|---|
| **全局面板** | 集团/CEO | harness 事件 + portal 表 | 各部门运作状态；**每个员工（自然人 + 数字员工）正在干的活**；人机比；预算消耗；异常红黄灯 |
| **项目看板** | PMO/项目经理 | `new_project` / `new_task` / `new_prjtresource` / `projectemp` | 项目概览、进度、里程碑、风险、阻塞项、责任矩阵（RACI） |
| **销售看板** | 销售总监 | `intentfollow_up` / `saleorder` / `contract` / `customer` | 线索漏斗、商机阶段、回款风险、"销售自主接单"的新增与转化 |
| **运维看板** | 运维总监 | `servermonitor` / `upserver` / `cdn_logs` / `t_logtab` / `executerecord` | 资产健康、告警队列、**自主修复率/误修率/待审批修复**、变更窗口 |
| **工作组巡查（上帝视角）** | 部门主管/集团 | harness 全量事件流 + portal 消息/任务/群聊 | 进入任意工作群/会话查看工作过程；按 Agent/人类/时间线检索；**只读**，不干预 |
| **主管谈话（抽调）** | 部门主管 | harness 轨迹 + `worklog` | 选员工（可含数字员工）→ 自动生成"工作内容摘要 + 卡点 + 风险 + 建议"→ 主管提问 → 形成**谈话报告**（结论 + 决定）→ 报告给上级 → **可触发岗位重新设计**（修改 `workposition`） |

### 12.1 主管谈话 → 岗位重新设计（闭环）

```
[抽调] 主管选择员工(人/AI) → 系统生成"事实包"(做了什么/做到哪/卡在哪/协作方评价/超时情况)
   ↓
[面谈] 主管与员工对话（AI 员工提供结构化自述 + 答辩）
   ↓
[结论] 主管形成结论与决定（保留原话，转写为结构化字段）
   ↓
[上报] 生成报告 → 提交上级（部门经理/人力资源）→ 归档
   ↓
[执行] 若结论涉及职责调整 → 生成 `workposition` 变更单（改 workcontent / functionIDs / permissions）
      → 变更后：数字员工自动降权/提权 → 相关会话与待办重新路由 → 旧版本留存可回滚
```

**为什么这条链路能成立**：因为 portal 的权限本就挂在 `workposition` 上（§2.1 结论 A）。**"给数字员工重新设计岗位"= 修改岗位定义 + 重新绑定**，是 portal 天然支持的，不需要新造轮子。真正的新增是 harness 侧的**变更影响分析**（改岗位会影响哪些在办任务/群组/审批）与**变更后自动重路由**。

### 12.2 "上帝视角"的伦理与安全边界

- **只读、且有边界**：可查看工作群/会话，但**不能**静默长期潜伏。必须有：① 访问需授权（主管角色 + 目标范围）；② 每次访问留痕并在被查看者侧**可见**（"XX 主管查看了本群"）；③ 会话内容中的敏感字段自动脱敏；④ 访问频次上限。
- 这条不是洁癖：没有透明性的监控会让员工与 AI 员工都学会规避，反而摧毁"数字员工真干活"的前提。

## 13. 系统升级与业务系统 A/B 发布

### 13.1 两条流水线合一（重要决策）

原始诉求分别列了"系统升级"和"业务系统 A/B 发布"。**必须用同一条流水线**，否则会出现"自主修复改了 A 版本、B 版本行为不一致"的经典事故。

```
[变更来源] 人工提交 | 大脑提案 | 自主修复 | 业务需求生成
     ↓
[编译/打包] 产出不可变制品 (artifact) + 哈希 + SBOM
     ↓
[静态检查] 语法/依赖/密钥扫描/许可证
     ↓
[自动测试] 单元 + 集成（沙箱）
     ↓
[影子流量] 真实请求复制 → 新版本并行执行 → 结果比对（diff）  ← 自主修复必经此步
     ↓
[评测] harness 评测集回归 + 回归用例集
     ↓
[灰度] 1% → 10% → 50% → 100%（每档观察期自动评估，不达标自动回滚）
     ↓
[全量] 观察期结束 → 固化
     ↓
[归档] 制品、diff、评测、审批、责任人全链留档
```

### 13.2 A/B 与分流

- 分流维度：员工（`employee.id`）、部门、任务类型、请求特征。**同一员工在稳定哈希下始终落在同一组**，避免用户体验抖动（数字员工尤其敏感于上下文连续性）。
- **数字员工参与验证**：让数字员工充当"虚拟用户"跑业务用例（回归）。这既验证了系统，也验证了数字员工本身。

### 13.3 回滚

- 回滚必须**一键、且在 60 秒内完成**（A/B 的价值就在这里）。
- 自动回滚触发条件：错误率上升、关键指标偏离、**自主修复产生的 diff 超出预期**、灰度期出现 P0。
- 回滚后必须自动生成**事故单**，进入改进闭环（§14）。

## 14. 自我进化闭环

原始诉求："工作中积累经验或者技能，下次类似的工作就能快速完成"、"大脑自我训练：收集集团所有资料然后定时训练"、"经验体上传/下载"。

### 14.1 三层记忆模型

| 层 | 内容 | 存储 | 生命周期 | 是否可自改 |
|---|---|---|---|---|
| **情景记忆 (Episodic)** | 每次任务的完整轨迹：输入、过程、工具调用、结果、错误 | `harness_experience` | 长期 | **否**（只追加，不可改写） |
| **程序记忆 (Procedural)** | 可复用的技能/流程：步骤、模板、检查清单 | `harness_skill`（版本化 + 签名） | 长期 | **是，但需评审与灰度** |
| **语义记忆 (Semantic)** | 事实性知识：产品资料、客户信息、制度、组织架构 | `harness_knowledge` + 外部向量库 | 中期 | **否**（知识有 owner 与生效审批） |

> **关键纪律**：**情景记忆不可被 AI 改写**。一旦允许改写，等于允许"篡改历史以掩盖失败"，归因和复盘全部失效。

### 14.2 进化流水线

```
[采集] 任务成功/失败/被打回/被降权 的完整轨迹
   ↓
[归因] 大脑分析：成功因子 / 失败因子 / 当时的上下文 / 可复用的抽象
   ↓
[候选] 生成候选技能 / 候选提示模板 / 候选工具参数表
   ↓
[准入] 静态检查（是否含越权动作、是否含注入风险、是否有外部依赖）
   ↓
[评测] ① 离线回放集（历史任务重跑） ② 沙箱执行 ③ 对抗测试（恶意输入）
   ↓
[评审] 管理态 Agent 评审 + 阈值内可自动通过（如仅格式化、不改语义）
   ↓
[发布] 签名 → 灰度（5% 任务）→ 指标对比 → 全量 / 回滚
   ↓
[下发] 推送到终端（经验体下载）；大脑侧索引更新
```

### 14.3 自我训练

- **数据集来源**：企业资料（`knowledgelib`、文档站、Git、邮件与工单历史）。**必须先过合规过滤**：PII 脱敏、版权/密级标注、员工同意、离职员工数据清理。
- **训练流水线**：数据抽取 → 清洗去重 → 质量/密级检查 → 训练 → 评测集（留出集，**不可参与训练**）→ 安全评测（是否学到越权指令）→ 影子部署 → A/B → 发布。
- **禁止自举**：**禁止用模型自己产生的输出作为下一轮训练数据**，除非经过人工抽检比例 ≥ 5% 并通过质量门。否则模型会快速熵增（model collapse）。
- **模型版本与回滚**：每个模型有 `model_version`，线上保留 ≥ 2 个版本，支持热切回。

### 14.4 自动降级与熔断（自我进化的安全阀）

| 指标 | 阈值 | 动作 |
|---|---|---|
| 审批驳回率 | 7 日 > 30% | 自治等级 -1 |
| 任务失败率 | 7 日 > 15% | 自治等级 -1，生成归因报告 |
| 熔断触发 | 任意一次 | 立即降到 L0/L1，人工介入 |
| 人工纠正频率 | 单任务 ≥ 3 次纠正 | 暂停自主执行，生成经验候选（走评审） |
| 成本超支 | 日预算 120% | 切本地模型 / 排队 |

> **反直觉的设计**：**降低自主性是默认的失败响应**。多数系统会奖励"多做事"，这里必须奖励"少出错"。

## 15. 成本与效能模型

### 15.1 成本项

| 项 | 单价 | 说明 |
|---|---|---|
| 终端硬件 | 5.0 万元/台（5090 主机） | 一次性 |
| 电费 | 450 元/月/台 | ≈ 0.65 元/小时（按 700h 计） |
| 年化硬件+电费 | ≈ 10.4 万元/台 | 不含折旧口径差异 |
| 云端大脑（满血版模型） | 按 token 计 | 弹性，用量随"自主任务数"增长 |
| 存储与带宽 | 小 | 经验体/日志/知识库 |

### 15.2 效能口径（必须定义，否则无法证明降本）

- **替代工时**：`Σ(数字员工完成任务的人工预估工时 × 完成率 × 质量系数)`。
- **人机比**：自然人 FTE : 数字员工数（按有效工时折算）。
- **自主率**：无需人工介入即闭环的任务占比（目标：M2 阶段 ≥ 60% 对 L≤2 的任务）。
- **修复率 / 误修率**：自主修复占故障总数比例 / 其中被回滚或造成二次故障的比例。**误修率必须单独公示**，否则指标会被"自主率"掩盖。
- **看板红线**：若某数字员工的"误修率 > 3% 或 人工纠正 > 2 次/周"，平台自动建议下线并生成复盘。

### 15.3 退役机制

每个数字员工有：`任职期 KPI`、`退役触发条件`、`交接包`、`下线流程`（停权 → 经验归档 → 权限回收 → 终端解绑 → 记录归档）。**能进能出**是"数字员工"区别于"僵尸机器人"的关键。

## 16. 安全与治理基线

| 域 | 基线要求 |
|---|---|
| 身份 | 终端 mTLS 双向认证 + 设备证书；Agent 独立凭证，不复用 portal Cookie；联邦用短期 capability token |
| 凭据 | 密钥不落业务进程；凭据保险库；**日志/上下文自动脱敏**（密码、身份证、卡号、客户联系方式） |
| 最小权限 | 默认 L0；权限从岗位继承；提权需审批 + TTL；禁止常开高权 |
| 审计 | 事件总线全量留存 ≥ 180 天；自主动作可回放（输入/推理摘要/工具调用/输出/审批） |
| 数据 | 出境/出域前过 DLP；训练数据脱敏 + 密级；终端本地缓存加密 |
| 指令注入 | **数据与指令双通道**：外部内容（邮件/文档/群消息）默认标记为 `untrusted`，不得直接转为工具调用；模型侧强制"引用才可执行" |
| 变更 | 生产变更走 §13 流水线；自主修复必须影子比对 |
| 熔断 | 全局 kill-switch（暂停所有自主执行）+ 分域 kill-switch |
| 合规 | 数字员工的产出物在合同/财务/人事场景下必须有人类签署；AI 使用披露 |

## 17. 与 portal 的集成接入（工程细则）

### 17.1 集成方式选择

| 数据/能力 | 方式 | 说明 |
|---|---|---|
| 读组织/员工/岗位/权限 | **portal DB 只读账号**（视图或直连 + 严格 SQL 审计） | 简单且实时；风险是 schema 漂移 |
| 读任务/项目/工单/日志 | 同上 | 同上 |
| 写任务/日志/消息 | **独立 API 服务**（Struts2 新命名空间 `/api/harness/**`） | 走 portal 的业务逻辑与校验，避免绕开规则 |
| 写 `employee`/`users`/`workposition_employee` | **API 服务** | 入职动作必须走 portal 逻辑以触发其缓存刷新 |
| 实时事件 | portal → harness **事件推送**（HTTP Webhook / MQ）+ harness 轮询兜底 | 不能只靠轮询 |
| 外部系统 | MCP / OpenAPI | 不直连库 |

### 17.2 关键工程约束（来自现有代码）

1. **新增 API 必须登记 `functioninfo`**：因为 `LoginInterceptor` 用 `linkFunctionPage like '%dourl%'` 反查功能 ID，权限体系是 URL 驱动的。harness API 走**独立拦截器**（不注册进 `functioninfo` 的功能树，避免污染真人菜单），但在内部**映射**到 `functioninfo` 的功能 ID 以便复用权限判定。
2. **不要复用 `users.password`**：AI 账号在 `users` 里要有行（否则无法选人、无法进待办），但认证走 harness 侧的服务账号 + 签名，portal 侧的 AI 账号登录入口对人类不可见（可在 `users.status`/标记位上区分）。
3. **`executerecord` 是取证金矿**：`executerecord` 有 5.4 万行、内容形如"修改了一个员工的信息。"、`entityName`、`entityId`、`seenEmpId`。**自主修复的取证、对账、回放都应建立在这张表 + harness 事件表之上**。建议：**不改动它的写入语义**，而是在 harness 侧建 `harness_audit` 与它做 `entityId/entityName` 的关联索引。
4. **时间字段全是 `varchar`**：`worklog.recordTime`、`mission.build_time` 是 datetime，但 `scheduleplan.begintime`、`new_task.begintime` 是 varchar。适配层必须做**严格的解析 + 失败告警**，否则时间线排序会静默出错。
5. **逗号分隔 ID 列表**：`workposition.functionIDs`、`role_function_info.permissions`、`user_group_info.groupIDs` 都是字符串。harness 侧要做**解析 + 缓存 + 失效**，不能每次全表扫。
6. **表引擎混用**：`projectemp`/`projectemp`/`projectlead` 是 **MyISAM**（无事务、无外键）。涉及这些表的写入要单事务设计，不能指望回滚。
7. **字符集 `utf8_general_ci`**：跨库连接要显式设置 `character_set_results=utf8`，避免中文乱码导致"看起来没数据"。

### 17.3 portal 侧最小改造清单（尽量少）

| 改造 | 类型 | 必要性 | 风险 |
|---|---|---|---|
| 新增 `/api/harness/**` Struts2 命名空间 + 独立拦截器（服务账号 + 签名 + 限流） | 新增 | 必须 | 低（不改动既有路径） |
| `users` 表加 `isAI` 标记位（或用 `mark` 约定值） | 加列/约定 | 必须 | 低 |
| `employee` 增加 `agentRef` 字段（harness agent uuid） | 加列 | 必须 | 低 |
| `functioninfo` 增加 harness 专用子节点（仅权限映射用，不显示在真人菜单） | 加数据 | 必须 | 低 |
| 事件推送出口（在任务/消息/审批写入后发 Webhook） | 新增 | 强烈建议 | 中（需在既有写入点加钩子） |
| 消息表增加"由数字员工发送"的可识别位 | 加列/约定 | 建议 | 低 |

> **改造总量目标**：portal 侧改动 **≤ 8 处、≤ 1500 行**，且全部为**新增**而非修改核心流程。任何"重构 portal 权限体系"的想法在本期**明确否决**（见 `02-对抗评审.md` D-03）。

## 18. 风险登记册（摘要，详见 `02-对抗评审.md`）

| ID | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R-01 | 终端绑定后等于"员工全部权限"= 高价值单点失陷 | 高 | 权限收敛为"账号权限 ∩ 设备白名单 ∩ 能力 TTL"，mTLS，设备可秒级吊销 |

| R-04 | 自我进化导致越权能力固化 | 高 | 技能签名 + 离线回放评测 + 灰度 + 一键回滚 + 情景记忆不可改写 |

| R-07 | 权限判定基于 URL，harness API 易越权 | 中高 | 独立拦截器 + functioninfo 映射 + 权限回归测试 |
| R-08 | 老 schema 拖垮新系统（varchar 时间、逗号 ID、MyISAM） | 中 | 适配层 + 严格解析告警 + 规范化镜像库 |
| R-09 | 自主修复误修引发二次故障 | 中高 | 影子比对 + 变更窗口 + 误修率公示 + 自动降级 |

| R-12 | 老员工抵触与信任崩塌（尤其"上帝视角"） | 中 | 透明化监控 + 只读 + 访问可见 + 员工可申诉 |
