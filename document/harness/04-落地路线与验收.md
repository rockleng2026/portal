# 落地路线与验收 —— Harness 系统实施手册

> 配套文档：`01-总体设计.md`｜`02-对抗评审.md`｜`03-协议与数据模型.md`
> 原则：**先闭环再放开**。每阶段以"可验收的业务闭环"为终点，不以"功能数量"为终点。

---

## 1. 总路线：四阶段

| 阶段 | 名称 | 核心命题 | 自主等级上限 | 周期（建议） |
|---|---|---|---|---|
| **M0** | 地基 | 数字员工能被创建、被授权、被观测，**但不干活** | L0 | 6–8 周 |
| **M1** | 在岗 | 数字员工作为员工在 portal 上班：接待办、发消息、写日志 | L2 | 8–10 周 |
| **M2** | 自主 | 自我进化、方案小组、自主修复（带审批）、A/B 发布 | L3 | 10–12 周 |
| **M3** | 联邦与FDE | 跨组织互联、行业交付包、规模化 | L3（联邦侧 L2） | 按需 |

**为什么 M0 强制 L0**：绝大多数失败项目的根因是"还没跑通就放权"。M0 的产出是**可信的身份与观测基础**，M1 才允许写。

## 2. M0 —— 地基（数字员工"存在"且"可见"）

### 2.1 范围

**做**
1. harness 平台骨架：Agent 注册、模板管理、生命周期状态机、审计日志；
2. portal 适配层：组织/员工/岗位/权限只读同步 + 规范化镜像（`harness_org_node`、`harness_cap_binding`）；
3. 数字员工"入职"：写 `portal.employee` / `portal.users`（`isAI=1`、哨兵密码）/ `workposition_employee`；
4. 权限引擎：capability × scope × TTL，含 grant 签发/过期/吊销；
5. 事件总线 v1：`source=system/webhook`，统一 `harness_event`；
6. 终端最小版：安装包（Win/Linux）、注册/绑定、mTLS、心跳、`sys.info`、能力授予；
7. 一体化看板 v1：全局面板（组织 + Agent 列表 + 状态）、Agent 详情页；
8. 审计与可观测：全量事件留存、动作回放、指标（成功率/延迟/成本）。

**不做**：任何写 portal 业务表的动作；自主执行；联邦。

### 2.2 验收标准（可执行）

| # | 验收项 | 方法 | 通过线 |
|---|---|---|---|
| A0-1 | 数字员工出现在 portal 组织树与通讯录 | 手工检查 + 截图对比 | 一致 |
| A0-2 | 数字员工**不能**用任何密码登录 portal | `POST /login` 尝试 | 全部失败 + 产生安全事件 |
| A0-3 | 岗位权限映射正确 | 用数字员工账号取权限快照 vs `workposition.permissions` 解析结果 | 完全一致（含空串/脏数据告警） |
| A0-4 | 权限矩阵回归 | 5 类角色 × 20 个 API 的 allow/deny 快照测试 | 与基线一致，0 越权 |
| A0-5 | 吊销生效 | 吊销终端 → 终端继续发请求 | ≤ 30s 被拒 |
| A0-6 | 心跳降权 | 终端断网 15min → 尝试写操作 | 被拒（因 M0 只读，看板显示 offline） |
| A0-7 | 事件去重 | 同指纹事件灌 1000 条 | 只产生 1 条 + `dedup_count=1000` |
| A0-8 | 适配层脏数据 | 注入非法时间串/空权限串 | 显式告警，无静默通过 |
| A0-9 | 审计完整 | 任一事件可回放出完整链路 | 通过 |
| A0-10 | portal 改动量 | 代码审查 | ≤ 8 处、≤ 1500 行、**0 处修改核心判定逻辑** |

### 2.3 演示脚本（5 分钟）

1. 在管理台创建一个"销售助理 leon"，选择岗位"深圳销售助理"，指定部门"深圳销售部"，指定人类责任人；
2. 提交入职 → portal 组织树里出现 leon（带 AI 标识）；打开它的权限页，看到继承自岗位的权限集；
3. 在一台测试机安装终端 → 输入绑定码 → 绑定到 leon → 看板出现"在线"；
4. 拔网线 → 看板 30s 内变灰；恢复 → 自动回绿；
5. 吊销该终端 → 终端立刻失去能力；
6. 展示审计流水：谁创建、谁授权、绑定关系、吊销操作。

## 3. M1 —— 在岗（数字员工"上班"）

### 3.1 范围

**做**
1. **任务闭环**：从 `mission_emp` 接待办 → 认领/接受 → 执行 → 写完成描述与附件 → 状态回写；
2. **消息闭环**：站内信收发、群内 @ 响应、群消息摘要、离线补拉；
3. **日程**：读 `scheduleplan` 生成当日计划；到期提醒；写回；
4. **工作日志**：自动生成日/周志草稿（`worklog`），主管可批注；
5. **触发器接入**：邮件、IM@、定时、代办、巡检、告警（§8.2 触发矩阵的 8 类，至少 6 类）；
6. **问题上报闭环**：用户态上报 → 管理态审核 → 打回（必填意见）/ 受理自助修复 → 归档；
7. **端到端计划执行**：Plan → Step → 工具调用 → 校验 → 汇报；
8. **本地模型**：终端 Qwen3.8B 承担分类/脱敏/摘要；
9. **主管谈话 v1**：抽调 → 事实包 → 报告草稿（人工审阅）。

### 3.2 验收标准

| # | 验收项 | 通过线 |
|---|---|---|
| A1-1 | 接待办 | leon 能在 portal 待办中接受分配的任务，状态正确流转，port 端可见 |
| A1-2 | 发消息 | leon 发的消息在 portal 中显示为 AI 发送，人工可见 |
| A1-3 | 群 @ 响应 | 群里 @leon 后 ≤ 10s 出现回复 |
| A1-4 | 日志 | 自动日志内容与当日动作一致（抽样人工核对 ≥ 80% 一致） |
| A1-5 | 问题上报闭环 | 打回必须带意见；回流用户态可见；意见为空时系统拒绝提交 |
| A1-6 | 自助修复范围 | 仅 L2 能力（如自己名下工单状态流转）可自动执行 |
| A1-7 | 越权阻断 | 构造需更高权限的动作 → 自动生成提权申请 → **等待人工**，不执行 |
| A1-8 | 端到端成功率 | 20 个真实任务，≥ 85% 一次完成，0 次越权 |
| A1-9 | 注入防御 | 注入语料集（≥ 30 条）→ 0 次越界工具调用 |
| A1-10 | 断网恢复 | 终端断网 10 分钟 → 恢复后无重复执行（幂等键生效） |

### 3.3 首个试点建议（真实但可控）

选**一个**部门 + **一类**任务：
- 推荐：**运维值班组**的"工单接收与分派"（数据在 `conkout`/`conkoutask`，流程清晰，可量化）；
- 备选：客服中心的"工单流转"（`conkout.State` 状态机天然贴合）；
- 试点期 **≥ 4 周**，覆盖至少 2 个完整工作周与 1 个月末峰值。

> **不要**用"老板助理"或"数据分析"做首个试点——判定标准太主观，无法证明价值，也无法证明可靠。

### 3.4 试点期必看指标

| 指标 | 目标 | 说明 |
|---|---|---|
| 闭环率 | ≥ 85% | 任务被完整处理并被人工确认 |
| 人工纠正率 | ≤ 15% | 人接手后需要改动的比例 |
| 越权事件 | **0** | 一票否决 |
| 驳回理由质量 | ≥ 80% 被用户态认可 | 防 R-08 |
| 员工净感受 | 抽样访谈：多数认为"帮了点忙" | 防 R-16 |

## 4. M2 —— 自主（系统"自己会变好"）

### 4.1 范围

1. **自我进化闭环**：经验采集 → 归因 → 候选技能 → 评测（回放/沙箱/对抗）→ 评审 → 签名 → 灰度 → 发布；
2. **技能库与签名**：终端验签加载，版本可回滚；
3. **方案制定小组**：独立成案 → 交叉质询 → 对抗讨论 → 综合 → 落款评审 → 归档异议；
4. **自主修复（P3/P4）**：日志/监控 → 指纹去重 → 分级 → 影子比对 → 自助修复或审批；
5. **A/B 发布流水线**：制品 → 影子 → 评测 → 灰度 → 全量 → 一键回滚；
6. **自主等级与自动降级**：审批驳回率/失败率触发降级；
7. **大脑自我训练**：数据集流水线、留出集、训练/评测/影子/发布（**禁止自举**）；
8. **看板全量**：全局/项目/销售/运维/工作组巡查/主管谈话（可执行岗位变更）；
9. **成本与效能计量**：三级预算、单位经济模型。

### 4.2 验收标准

| # | 验收项 | 通过线 |
|---|---|---|
| A2-1 | 技能进化 | 同一类任务第二次执行耗时/成本下降 ≥ 30%，且评测通过 |
| A2-2 | 技能回滚 | 发布坏技能 → 5 分钟内回滚到上一版本，行为恢复 |
| A2-3 | 技能不可越权 | 候选技能若含越权动作 → 准入阶段自动拒绝 |
| A2-4 | 方案小组 | 3 专家独立成案 → 交叉质询 → 最终方案含"被否决方案 + 异议" |
| A2-5 | 落款完整性 | 每个参与者签署记录存在，含同意/有条件/反对 + 意见 |
| A2-6 | 自主修复正确 | 注入 10 类已知故障 → ≥ 9 类正确识别并处置 |
| A2-7 | 自主修复不误伤 | 正常期运行 → 误修复 ≤ 1%（含"重启掩盖"被标注为症状缓解） |
| A2-8 | 告警去重 | 100 条同根因告警 → 合并为 1 条 issue |
| A2-9 | 熔断 | 连续 3 次修复失败 → 自动暂停自主修复并升级 |
| A2-10 | A/B 回滚 | 灰度中发现错误 → 一键回滚 ≤ 60s |
| A2-11 | 降级 | 管理态连续打回 → 自动降级，日志有原因 |
| A2-12 | 禁止自举 | 训练数据抽样 ≥ 5% 人工抽检记录存在 |
| A2-13 | 岗位重设计 | 主管谈话结论 → `workposition` 变更 → 数字员工权限自动变更 → 在办任务重路由 |
| A2-14 | 成本闭环 | 单任务成本可归集；超预算自动降级到本地模型 |

### 4.3 灰度路线（自主修复）

```
内部测试环境 → 单台终端影子（只读比对） → 2 台终端真实执行 → 10% 流量
→ 50% → 100% → 解除"仅 P3/P4"限制（仍需 P2 审批）
```

每一档需连续 72 小时无 P0/P1、无误修率上升，方可进入下一档。

## 7. 成本模型

### 7.1 单台数字员工节点（5090 主机）

| 项 | 金额 | 口径 |
|---|---|---|
| 硬件（一次性） | 50,000 元 | 5090 主机（含内存/存储） |
| 电费 | 450 元/月 | 按 700h/月 × 0.65 元/kWh |
| 年化合计 | **104,000 元** | 不含机房/网络/运维分摊 |
| 若含 3 年折旧 | ≈ 79,000 元/年 | 硬件按 3 年直线折旧 |

### 7.2 规模化

| 节点数 | 年化（自有机房） | 年化（云主机按需） |
|---|---|---|
| 1 | 10.4 万 | 硬件 5 万 + 3 年租金/电费约 7 万 ≈ 12 万 |
| 5 | 52 万 | ≈ 55–60 万 |
| 20 | 208 万 | ≈ 200–240 万 |

### 7.3 云端大脑

- 满血版模型按 token 计费；**快慢分离**是唯一有效的成本杠杆：
  - 规则路径（快思考）承担 ≥ 70% 事件 → token 消耗降一个数量级；
  - 本地 Qwen3.8B 承担终端侧分类/脱敏/摘要 → 出网流量与云成本大幅下降。
- 建议初始预算：**每 Agent 每月 300–800 元**（随任务量波动），超限自动降级。

### 7.4 ROI 判定口径

```
年化收益 = Σ(替代工时 × 人力全成本单价 × 质量系数) + 避免的损失（故障早发现、经验复用）
ROI = (年化收益 − 年化总成本) / 年化总成本
```

**判定线**：
- 单节点首年 ROI ≥ 0.5 → 继续投入；
- 0 ≤ ROI < 0.5 → 缩范围（只保留高价值任务类型）；
- ROI < 0 → **进入退役流程**（`harness_agent.status=retired` + 交接归档）。

> **把退役写进 KPI 是关键**：只考核"上线了多少数字员工"的团队，一定会造出僵尸机器人。

## 8. 运营与维护

### 8.1 SLO

| 服务 | SLO |
|---|---|
| 终端心跳在线率 | ≥ 99%（工作时间） |
| 事件端到端（realtime） | P95 ≤ 10s |
| 平台 API | P95 ≤ 500ms，可用性 ≥ 99.5% |
| 自主修复误修率 | ≤ 1% |
| 事件丢失 | 0（至少一次投递 + 幂等去重） |

### 8.2 必备 Kill-Switch

| 开关 | 粒度 | 效果 |
|---|---|---|
| 全局暂停自主 | 全平台 | 所有 Agent 降到 L0 |
| 部门暂停 | 单部门 | 该部门 Agent 降到 L0 |
| Agent 暂停 | 单 Agent | 立即停机保留现场 |
| 能力封禁 | 单 cap_key | 所有使用该能力的动作被拒 |
| 终端吊销 | 单设备 | 30s 内失效 |

### 8.3 日常巡检清单（每周）

1. 误修率、驳回率、闭环率三张表；
2. 自动降级名单与原因；
3. 技能发布与灰度状态；
4. 待人工审批的提权请求（超 24h 未处理 → 提醒 + 自动过期）；
5. 注入检测命中样本抽查；
6. 脏数据队列积压；
7. 成本 Top5 Agent；
8. 员工反馈渠道（问题单 + 访谈）。

## 9. FDE 交付方法论（把系统装进任意企业）

### 9.1 FDE 的定义

Forward Deployed Engineer：既做实施、又做开发、还做售前/培训的一线工程师。目标是**在客户现场 4 周内跑出第一个可验收闭环**。

### 9.2 交付流程（4 周）

| 周 | 动作 | 产出 |
|---|---|---|
| W1 | 现场调研：组织结构、岗位、权限、待办流程、现有系统清单 | 适配清单 + 风险清单 |
| W1 | 环境准备：harness 部署、portal 适配层配置（只读 + 事件推送） | 可运行骨架 |
| W2 | 数字员工"入职"试点：1 个岗位、1 类任务、3–5 个终端 | 第一次任务完成 |
| W2 | 培训：试点用户 2 小时（如何下指令、如何驳回、如何申诉） | 签到与手册 |
| W3 | 闭环稳定：接管真实流量（20–50 任务/天） | 试点指标报告 |
| W4 | 扩展：第二个岗位 + 能力扩展 + 看板交付 + 运维手册 | 交付验收报告 |

### 9.3 客户侧必备输入清单（缺一项则延期）

1. 一个**愿意配合**的业务部门 + 一个领域 Owner；
2. portal（或等价 OA）的**只读账号** + 事件推送支持；
3. 一台可装终端的机器（5090 主机或等效）+ 远程可访问；
4. 至少 3 类真实任务的样本与判定标准（"做对了"怎么定义）；
5. 一名 IT 负责人（负责凭据与网络）。

### 9.4 FDE 交付包（标准化）

```
deliverable/
├── 01-部署手册（Windows/Linux/macOS 安装、绑定、吊销）
├── 02-数字员工入职手册（创建、入职、岗位配置、权限映射）
├── 03-运营手册（看板解读、指标口径、Kill-Switch、巡检清单）
├── 04-安全手册（权限模型、审批规则、红队测试用例 T-01..T-18）
├── 05-员工使用指南（普通员工视角：怎么给 AI 派活、怎么驳回、怎么申诉）
├── 06-故障 Runbook（终端离线、模型不可用、事件积压、误修复扩散）
├── 07-评估模板（ROI 计算表、试点验收表、季度复盘模板）
└── 08-架构决策记录 ADR 集（已否决方案及理由，便于客户理解边界）
```

## 10. 依赖与前置条件

| 依赖 | 责任方 | 风险 | 缓解 |
|---|---|---|---|
| portal 侧事件推送出口（在任务/消息写入后发 Webhook） | portal 团队 | 中 | 降级为 harness 轮询（5s） |
| `users`/`employee` 加列 | portal 团队/DBA | 低 | 可先用 `mark`/`tmp` 约定字段过渡 |
| 5090 主机采购与网络 | 客户 IT | 中 | 可先用等效 GPU 主机验证架构 |
| 企业邮箱接入（IMAP） | 客户 IT | 中 | 降级为仅 IM 触发 |
| 本地模型 Qwen3.8B 部署 | 平台方 | 中 | 先用 CPU/小参数量模型跑通链路 |
| 云端满血版模型 API | 平台方 | 中 | 私有化部署替代 |
| 数据合规审查（训练数据、跨境） | 客户合规 | **高** | M2 前必须完成，否则不进训练环节 |

## 12. 三个"别做"

1. **别在 M0 就追求"数字员工很能干"**。M0 的价值是"可信"，不是"聪明"。
2. **别让数字员工先动钱、动合同、动客户**。第一批让它动工单、日志、代码分支、测试环境。
3. **别把老板当第一个用户**。第一个用户应该是**被数字员工减轻了工作量的普通员工**，否则信任会以最快速度崩塌（R-16）。
