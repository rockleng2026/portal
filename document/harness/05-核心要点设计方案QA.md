# Harness 核心要点设计方案 QA

## Q1: 为什么数字员工不能用任何密码登录 portal（A0-2）？

### 设计出发点

| 维度 | 设计决策 | 核心理由 |
|---|---|---|
| **认证体系分离** | `POST /login` 全部失败 + 产生安全事件 | 门户(portal)使用传统 Cookie/密码体系；harness 使用独立的 HMAC 服务账号认证。二者有意隔离，避免凭据体系冲突（ADR-004） |
| **最小权限原则** | 无法登录 → 所有动作通过 harness API / 事件总线 | 如果数字员工能登录 portal，就必须授予其可逆密码或 Cookie，这会打开“可逆密码体系被复用”的安全隐患 |
| **审计不可篡改** | 登录失败 → 安全事件被记录 | 所有登录尝试（无论成功失败）都被记录在审计链路中，便于异常检测 |
| **FDE 先闭环后放开** | M0 强制 L0，仅做“存在+可见”，不做“能干” | 先建立可信身份与观测基础，再决定授权范围。若 M0 就授予登录权，将失去后续阶段的控制边界 |

### 技术实现

**数字员工的 portal 身份是“镜像”，而非“用户”**：

```yaml
# portal.employee 表中的 AI 账号记录（而非真实员工）
isAI: 1           # 标记为数字员工
sentinel_password: "<强随机串，仅用于身份校验，不可登录>"
# 登录时的行为：
POST /login {loginName: "agent:leon:sales:sh001", password: "anything"}
# → 返回 401 + 审计事件：AI 账号登录尝试被拒
```

**数字员工的真实认证发生在 harness 层**：
- `Harness-Auth` Header: HMAC signature over `timestamp + method + path + body`
- 通过 `POST /harness/exec` 等 API 与平台交互
- 所有动作带有数字签名，可追溯到具体的 Agent 实例

## Q2: 数字员工如何在不登录 portal 的情况下将进度反馈回系统？

### 闭环路径：`终端 → harness 平台 → portal 适配层 → 仪表盘`

```
[任务执行] 
      ↓ (通过 harness API / 事件总线)
[harness 事件总线: harness_event]
      ↓ (portal 适配层轮询/推送)
[portal 组织树 / 待办 / 活动面板 更新]
```

### 具体数据流转

| 步骤 | 组件 | 数据流向 |
|---|---|---|
| **1. 任务接受** | `mission_emp` 表 + 待办接口 | 数字员工通过 harness API `GET /missions/claim` 接受任务，状态写入 `mission_emp` |
| **2. 执行过程** | 本地模型(Qwen3.8B) + 工具调用 | 所有工具调用、中间结果由终端 Agent 本地记录，关键事件通过 `harness_event` 发送 |
| **3. 结果上报** | `worklog` + `harness_event` | 任务完成后，Agent 写入 `worklog` 并发事件：`{"type":"task_complete", "mission_id": "...", "result": "..."}` |
| **4. 门户展示** | 适配层 → 实时视图 | portal 适配层从事件总线订阅，实时更新“最近活动”表格和组织树状态 |
| **5. 审计留存** | ES / 日志库 | 全链路审计：谁在什么时间执行了什么任务，产出了什么结果 |

### 关键技术点

- **事件总线 v1**：`source=system/webhook`，统一 `harness_event` 主题。所有数字员工动作->事件->适配层->门户展示。
- **幂等键**：每个任务/动作有唯一指纹，防止重复执行或重复上报。
- **只读同步**：门户组织/员工/岗位数据是从 harness 单向同步的，写操作全部由 harness 完成。

## Q3: 管理员/领导如何看到数字员工的工作内容和进展？

### 三层可视化入口

| 入口 | 展示内容 | 适用角色 |
|---|---|---|
| **组织树/通讯录** | 数字员工账号（AI 标识）+ 继承的岗位权限集 | 所有人，便于查找和识别 |
| **实时大脑仪表盘** | - 五大能力点状态（主动/触发/自主/进化/委员会）<br>- 模型运行状态（规则/LLM/本地Qwen3.8B 计数）<br>- 系统概览卡片（总代理/在线/任务/月token/自主等级分布） | 运维、平台管理员 |
| **数字员工实时视图** | - 组织结构占位区块<br>- 代理卡片：姓名/在线状态/任务计数/完成进度<br>- 最近活动表格：时间/事件/详情/代理<br>- 快捷操作：接待办/发送消息 | 业务主管、团队领导 |

### 具体展示示例

**核心大脑仪表盘 指标**：

| 指标 | 示例值 | 含义 |
|---|---|---|
| 总代理数 | 24 | 系统中注册的数字员工总数 |
| 在线代理 | 17 | 当前在线、心跳正常的数字员工 |
| 进行中任务 | 42 | 当前正在执行的任务总数 |
| 本月 token 消耗 | 3.2M | 本月模型调用的总 token 数 |
| 自主等级分布 | L0:12, L1:8, L2:3, L3:1 | 各自主等级下的数字员工数量 |

**数字员工卡片 (leon - 销售助理)**：

| 字段 | 当前值 | 说明 |
|---|---|---|
| 姓名 | leon | 账号标识 |
| 在线状态 | 在线（心跳 2分钟前） | 最近心跳时间 |
| 今日任务数 | 3 | 今日接取的任务数 |
| 完成进度 | 2/3 (67%) | 已完成/总数 |
| 自主等级 | L1 | 当前自主等级 |

**最近活动表格**：

| 时间 | 事件 | 详情 | 代理 |
|---|---|---|---|
| 10:23:12 | 任务完成 | 工单A 状态变更为“已完成” | leon |
| 10:15:45 | 站内信发送 | 发送给客户：项目进度汇报 | leon |
| 09:50:00 | 任务领取 | 接受分配的工单B | leon |
| 09:30:22 | 模型调用 | Qwen3.8B 对工单内容进行分类 | leon |

### 领导/管理员视角的决策支持

1. **闭环率一瞥**：`≥ 85%` 的任务被完整处理并被人工确认——一眼看出团队效率
2. **越权零容忙**：任何越权尝试都会在审计日志中标记，管理员可快速定位
3. **人工纠正率 ≤ 15%**：如果数字员工需要人工介入的比例过高，说明任务类型或能力配置有问题
4. **成本看板**：单任务成本可归集，超预算会自动降级到本地模型——帮助管理成本控制

## Q5: 关键设计原则摘录

1. **安全边界**：数字员工故意不能登录 portal，避免可逆密码体系被复用（A0-2）
2. **事件驱动**：所有数字员工动作通过事件总线上报，实现门户实时展示
3. **只读同步**：门户数据由 harness 单向同步，避免双写不一致（ADR-008）
4. **分层自主**：M0-L0（存在可见）→ M1-L2（在岗任务）→ M2-L3（自主进化）→ M3（联邦FDE）
5. **成本控制**：快慢思考分离是唯一有效杠杆（≥70% 事件走规则路径）
6. **可审计**：全链路审计，所有动作带数字签名，可追溯到具体 Agent 实例
7. **Kill-Switch 五级开关**：全局/部门/Agent/能力/终端，任意一键降权或停机
8. **退役纳入 KPI**：防止僵尸机器人，退役流程写进关键考核指标

## Q6: 常见问题速览

| 问题 | 答案要点 |
|---|---|
| **数字员工能否直接在 portal 内操作** | 不能，所有操作通过 harness API + 事件总线，portal 仅负责展示和提供只读上下文 |
| **为什么不给数字员工可逆密码** | 会打开安全隐患，一旦泄露，攻击者可冲充任意数字员工；设计上有意隔离认证体系 |
| **管理员如何知道数字员工忙不忙** | 通过实时大脑仪表盘：在线数、任务数、完成进度、自主等级一目了然 |
| **任务完成进度如何同步到门户** | 通过 harness_event 总线：任务开始/进度/完成事件 → 适配层 → 实时更新待办/活动面板 |
| **如果数字员工“越权”了怎么办** | 审计日志标记，能力被封禁，自动降级至 L0，管理员需要人工介入批准或驳回 |
| **成本如何控制在可接受范围** | 本地 Qwen3.8B 承担分类/脱敏/摘要（70%+ 事件），云模型仅在需要复杂推理时调用；每 Agent 每月 300-800 元预算 |
